# Architecture decisions (Slices 0-5)

Each decision lists what was chosen, why, and what is deliberately deferred. Items marked **ASSUMPTION** are things
I decided without a business rule from you; please confirm or correct them.

## Shape
Modular monolith: one deployable, domain modules under `src/modules/<domain>` with their own schema, service and controller;
cross-module access goes through exported services only. Manufacturing is the first industry specialization, so the later
slices (inventory, costing, procurement, accounting) are designed with BOM/WIP/subcontractor concepts from the start; Slice 0
already has `raw_material`, `work_in_progress`, `finished_goods`, `scrap`, `quarantine`, `in_transit`, `subcontractor` warehouse kinds.
No microservices, Kafka or Kubernetes. Redis is not used.

## ADR-1 Platform: NestJS 12, TypeScript 6, ESM, strict
NestJS 12.4 is ESM-only (`module: nodenext`, `.js` import suffixes). Strict TypeScript with `noUncheckedIndexedAccess`.
Tests: Vitest; lint: oxlint (type-aware). Constructor injection uses explicit `@Inject(Class)` so the code behaves
the same under tsx/esbuild (no decorator metadata) and `nest build`.
**Dependency graph**: installs cleanly with strict peer resolution on **npm 11.21** and no `legacy-peer-deps`.
npm 10.9 crashes on this graph (arborist bug), so the repo pins `packageManager: npm@11.21.2`, `engines.npm >= 11`, and CI/Docker install npm 11.
Nest's first-party add-ons (outbox, idempotency, drizzle, locks, authn/authz) are pre-1.0, so integrity-critical parts are hand-written.

## ADR-2 HTTP adapter: Fastify default, Node adapter switchable
Both adapters pass the identical 55-test HTTP suite (the suite runs on both in CI) and the production build.
Measured on 4 vCPU, 32 connections, 6 s:

| scenario | Fastify | NodeAdapter |
| --- | --- | --- |
| GET /health/live | 16,188 req/s | 19,450 |
| GET /v1/tenant (DB, RLS tx) | 1,917 | 2,211 |
| list companies | 1,191 | 1,169 |
| POST company | 1,824 | 1,963 |

With any DB work the difference is noise (<15%). **Recommendation: Fastify**, for ecosystem maturity (plugins, hooks, schema tooling) and
because the code touching the adapter is a thin, adapter-agnostic layer (`HttpAdapterHost`). `HTTP_ADAPTER=fastify|node` keeps the switch; CI tests both.
This is a recommendation for your review, not a locked decision.

## ADR-3 Database: PostgreSQL, SQL-first migrations, Drizzle as typed query layer
The database is the source of truth: migrations are hand-written SQL (constraints, triggers, RLS, grants are not expressible in an ORM schema).
Drizzle's table definitions mirror them for typed queries; a test fails if the mirror drifts from the real columns.

## ADR-4 Tenancy and row-level security
Hierarchy: Tenant → Company → GST registration → Business location (branch) → Warehouse. A company has many GST registrations.
- Every business row carries `tenant_id`; primary keys are `(tenant_id, id)` and **every foreign key includes `tenant_id`**
  (FK integrity checks bypass RLS, so composite keys are what stop a cross-tenant reference).
- RLS is `ENABLE` + `FORCE` on every table with one policy `tenant_isolation` for role `erp_app`: `tenant_id = erp.current_tenant_id()`.
- The tenant is set per transaction with `set_config('app.tenant_id', $1, true)` (transaction-local), so pooled connections cannot leak a tenant. There is no bypass or platform mode.
- Runtime role `erp_app`: NOSUPERUSER, NOBYPASSRLS, owns nothing, no CREATE, only explicit `SELECT/INSERT/UPDATE` grants (**no DELETE**).
  Schema owner `erp_migrator` is a separate role used only by the migration runner. The app refuses to boot if the role is unsafe.
- A location must belong to a registration of its own company (composite FK `(tenant_id, company_id, gst_registration_id)`).

## ADR-5 Migrations
Forward-only SQL files `db/migrations/NNNN_name.sql`, each in its own transaction, sha256 checksum recorded in `erp.schema_migrations`,
guarded by an advisory lock. The runner rejects an edited, missing or out-of-order applied file and rolls a failing file back.
Readiness (`/health/ready`) fails if the database is behind the build's expected migration head.

## ADR-6 API conventions
Zod 4 validation through Nest's standard-schema pipe; OpenAPI generated from the same schemas.
Errors are RFC 9457 `application/problem+json` with stable `urn:erp:error:<code>` types; Postgres errors map to 409/422/403/503 without leaking SQL text.
Optimistic locking: rows have `version` (trigger-maintained); updates need `If-Match: <version>` (428 missing, 412 stale).
UUIDv7 ids, keyset pagination with opaque cursors. Request ids and security headers on every response; pino logs with secret redaction.

## ADR-7 Identity and authorization (Slice 1a)
- **Sign-in** is `tenant slug + email + password (+ MFA code)`. Passwords: **argon2id** (`@node-rs/argon2`, OWASP minimum profile; hashes carry their parameters and are upgraded on login). Length rule only (12+), no composition rules.
- **Access tokens**: EdDSA (Ed25519) JWTs, 15 min, hand-written on `node:crypto` (only EdDSA accepted, `kid` header, previous public keys can be listed for rotation). The token proves *who*; **permissions, user status, tenant status and session liveness are re-read from the database on every request** (one query), so a role change, disable or logout takes effect on the next request.
- **Refresh tokens**: opaque, 30 days, stored as SHA-256, **rotating**; each token is single-use and presenting a spent one revokes its whole session family (reuse detection). Concurrent double-refresh with one token will log that family out (stricter, no grace window).
- **MFA**: TOTP (RFC 6238, verified against the RFC vector), seed encrypted at rest with AES-256-GCM bound to tenant+user, each 30 s step usable once, 10 single-use hashed recovery codes.
- **Lockout**: N failures (default 5) locks the account for 15 min. Unknown tenant, unknown user, wrong password and locked account return the *same* 401 and do equal password-hash work.
- **API keys**: `ek_<tenant>_<id>_<secret>`, SHA-256 stored, shown once, explicit permission list, optional expiry, revocable (never deleted).
- **Authorization**: roles hold permission strings from a code-defined catalog; the built-in Owner role has `*`. **Default deny**: every route needs `@Public()` or `@RequirePermissions()/@Authenticated()`; a route that declares nothing returns 403. Nobody can grant a role, key or user more than they hold themselves; the last active owner cannot be removed or disabled.
- `tenant_directory` (slug -> id) is the one readable non-tenant mapping needed to start a sign-in; it is filled by a trigger and not writable by the runtime role.
- Not in this slice: SSO, password reset by email, invitations, per-IP rate limiting (belongs at the proxy/edge until Redis is introduced), branch/amount-limit rules (need documents to mean anything).

## ADR-8 Audit log (append-only)
Entries are written **inside the transaction of the change they describe** (no entry for a rolled-back change, none missing for a committed one). The runtime role has INSERT/SELECT only; a trigger also rejects UPDATE/DELETE/TRUNCATE from any role, superuser included. Auth events (login, failure, lockout, refresh-token reuse, password change, MFA), user/role/API-key changes and organization writes are recorded with actor, request id and IP; secrets are never recorded. Read with `GET /v1/audit-events` (newest first, filters, cursor). Tamper-evident hash chain deferred as agreed.

## ADR-9 Idempotency
`Idempotency-Key` on selected POSTs (optional by default, can be made required per route). The claim, the business work and the stored response commit **in one transaction** (the unit of work lets nested calls join the outer transaction), so there is no "in progress" state to get stuck in: concurrent duplicates wait on the unique key then replay; a failing request rolls the claim back and can be retried; a crash leaves nothing behind. Same key + different request or caller is 422. Keys expire (default 24 h) and are per tenant. Endpoints that return secrets (API key creation) deliberately do not use it, because the replay would have to store the secret.

## ADR-10 Transactional outbox
Events are inserted in the business transaction. A relay (in-process, optional, safe to run on several instances) delivers them **at least once** to registered consumers: `FOR UPDATE SKIP LOCKED` + lease, exponential backoff, parked as `dead` after N attempts with the last error (never dropped). Consumers are idempotent by construction: their effects and a `(event, consumer)` done-mark commit in one transaction. The queue table `outbox_dispatch` is **the second deliberate non-tenant table**: it holds only pointers (tenant id, event id, scheduling state), created by a trigger, so the relay can find work across tenants without the runtime role ever bypassing RLS; each event is read and handled inside its own tenant's context. No broker is involved (Postgres only), per the "no Kafka prematurely" direction.

## ADR-11 Document numbering
One series per **GST registration x document type x financial year** (no global counter). Allocation locks only that series row *inside the document's transaction*, so a number is consumed iff the document commits (no gaps from failures), and concurrent allocation is serialised per series only. Every issued number is kept in `number_allocations` forever; cancelling marks it cancelled and it is never reissued; the database allows only the single transition issued -> cancelled. Format = prefix + optional FY code + padded value, validated at creation so the widest possible number is <= 16 chars of `[A-Za-z0-9/-]` (rule 46 CGST). No HTTP endpoint hands out numbers; documents call `NumberingService.allocate` (Slice 5+).

## ADR-12 Ambient transactions
`UnitOfWork.inTenant` nested inside another `inTenant` for the *same tenant* joins it; a different tenant, or a write inside a read-only transaction, throws. This is what lets idempotency, audit, outbox and numbering participate in one atomic unit without threading `tx` through every signature, and it is the base for the later posting operations.

## ADR-13 Master data (Slice 2)
Currencies, exchange rates, units, tax codes with effective-dated rates, items, payment terms, parties (customers / suppliers / subcontractors as roles of one record), party addresses, price lists. Principles:
- **Effective dating is enforced by the database**: `EXCLUDE USING gist` (btree_gist, installed by the admin bootstrap into the `erp` schema) makes overlapping tax-rate or price periods impossible; a guard trigger lets a row be *closed* once and never rewritten or deleted. A rate change is one call: the open version is closed the day before the new one starts. Documents resolve the rate/price/exchange rate **for their own date**, so back-dated documents are right (`CatalogService.taxRateOn`, `PricingService.priceOn`, `CatalogService.rateOn`).
- **Manufacturing from day one**: item types `raw_material, packing_material, semi_finished, finished_good, trading_good, consumable, service`; `is_manufactured` only for semi-finished/finished; batch/serial tracking only for stocked items; per-item unit conversions (box of 12 -> factor 12); subcontractor role on parties.
- **Statutory checks live in both the API and the database**: HSN 4/6/8 digits, SAC 6 digits starting 99, GST UQC list for units, CGST = SGST = IGST/2, GSTIN format + check character, PAN inside GSTIN must match, registered treatments need a GSTIN and unregistered ones must not have one, PIN code only for Indian addresses.
- **Item identity is frozen**: code, type and base unit cannot change after creation (database trigger), because stock, costing and BOMs will depend on them.
- Money, quantities and rates are **decimal strings**, never floats. Exchange rates are immutable facts per date (correct by adding a new date); inverse rates are not derived.
- New tenants are seeded with INR and the 44 statutory units. **Tax rates are not seeded** (they are tenant configuration; a wrong default silently mis-taxes documents).

## ADR-14 Accounting core (Slice 3)
Chart of accounts, fiscal years/periods, the double-entry journal, trial balance and account ledger, per **company** (each company keeps its own books).
- **One posting door**: `PostingService.post(tx, ...)`. The manual-journal API and every future subledger (sales, purchases, stock, payroll, manufacturing) call it *inside their own transaction*, so a document and its ledger entry commit or roll back together, the entry number is returned on rollback, and a document cannot be posted twice (unique `(source type, source id, event)`; a repeat returns the existing entry).
- **Immutable ledger**: `journal_entries`/`journal_lines` have no UPDATE/DELETE/TRUNCATE for any role (triggers fire even for a superuser). Corrections are **reversing entries**: the mirror image, linked to the original, at most once, never reversing a reversal; entries created by a document can only be reversed through that document.
- **The database guarantees the invariants, the application only gives nicer errors**: a deferred constraint trigger checks at COMMIT that lines match the header and debits = credits; lines can only be added by the transaction that created the entry; the entry must fall in an **open** period containing its date; group and inactive accounts cannot be posted to.
- **Period locking**: `open <-> closed` (reopen needs its own permission, newest first; closing is in order) and `closed -> locked` (permanent). Posting takes the period row `FOR SHARE`, closing takes it `FOR UPDATE`: a close waits for postings in flight and later postings see the close, so nothing slips into a closed period (race-tested).
- **Posting controls**: manual journals cannot touch **control accounts** (receivables, payables, inventory, WIP, tax); only subledgers post there. This is how the later inventory subledger will reconcile to the GL without anyone editing the control accounts by hand.
- **Exact money**: amounts are decimal strings summed as integers of 1/10000; no floats anywhere.
- **Manufacturing from the start**: the opt-in starter chart (`POST /v1/companies/:id/chart-of-accounts/template`) has raw-material / packing / WIP / finished-goods / material-with-subcontractor inventory, GRNI, overheads absorbed, subcontracting, scrap, production variances and purchase price variance accounts. It is a convenience, not a policy: apply it, or build your own.
- Entry numbers `JV|OB|AJ|RV|SY/<FY>/<6 digits>` are per company x fiscal year x type (no global counter; not a statutory series).

## ADR-15 Inventory subledger (Slice 4a)
Decisions you made for this slice: **weighted average and FIFO per item**, **negative stock blocked by default with a per-warehouse override**, **batch (with expiry) and serial tracking**.
- **One entry point**: `StockService.move(tx, ...)`. It costs each line, enforces tracking and negative-stock rules, appends immutable ledger rows, updates balances/layers, and posts the matching GL entry via `PostingService`, all in the caller's transaction. Future purchasing, sales, production, transfers and counts call it with their own source (`goods_receipt:<id>` ...), so a document and its stock + GL effect are atomic and never applied twice.
- **Costing**: valuation is per **item per warehouse**. Weighted average derives the unit cost from balance value / quantity at issue time (no stored running average to drift); emptying a balance takes the exact remaining value, so no rounding residue stays. FIFO keeps cost layers (oldest *receipt date* first, not posting order) and records every consumption. All arithmetic is integer (qty and cost 6 dp, value 4 dp, half-up), never floating point. An item's costing method and tracking freeze once it has any movement (trigger).
- **Negative stock**: an issue beyond the balance is refused (409, with the available quantity) unless the **warehouse** allows negative stock **and** the item is weighted average; the shortfall is costed at the last known cost. FIFO items, batch balances and serial numbers can never go negative.
- **Batches/serials**: batch-tracked items need a batch on every line (created on receipt with optional manufacture/expiry dates); expired or blocked batches cannot be received or issued; serial-tracked items need exactly one distinct serial per unit and each unit moves in_stock -> issued.
- **GL link and reconciliation**: item type -> inventory control account is configured per company; opening stock and adjustments post against configured offset accounts; receipts/issues name their offset (HTTP callers cannot use control accounts, documents can). `GET /v1/inventory/reconciliation` compares, per stock account, the stock ledger value with the GL balance as of a date. Any difference is reported, `reconciled` is true only when all are zero. Because manual journals cannot post to control accounts, the two can only differ through a defect, which is exactly what this proves.
- **Locking**: balance rows are locked per (warehouse, item) in a fixed order (no deadlocks); 20 simultaneous issues against 10 units produced exactly 10 successes. Stock dates lock with the books: a movement needs an open accounting period.
- The stock ledger is append-only like the journal. Corrections are opposite movements; reversing a movement automatically (needed by document cancellation) arrives with the purchasing and sales slices that need it.

## ADR-16 Reservations, transfers and counts (Slice 4b)
All three change stock only through `StockService.move`, so ledger, balances and GL stay in agreement (re-asserted by the reconciliation in every test).
- **Reservations** hold quantity without moving it. Availability = on hand - active, unexpired reservations; other issues cannot take reserved stock (409 with `reserved` in the problem), an issue that names the reservation consumes it (partially or fully), and release/expiry give it back. Creating a reservation takes the *same balance-row lock* as a movement, so a reservation and an issue can never both claim the last unit. Batch-specific reservations protect that batch. Serial-tracked items are not reservable yet (issue by serial). Warehouses that allow negative stock can still be issued past reservations (the operator chose to relax stock rules there).
- **Transfers** are direct or two-step through an `in_transit` warehouse (dispatch now, receive later, partial receipts, cancel back to source if nothing was received). Stock moves at its own exact value, FIFO cost layers keep their cost *and receipt date*, batches and serial numbers travel (serials stay in stock and change warehouse). Because a transfer stays inside one inventory account it produces **no GL entry**; the in-transit warehouse keeps the value in the subledger. For weighted-average items the in-transit cost is pooled per item (two overlapping transfers of one item blend until received; total value is conserved).
- **Counts** snapshot the books, record what was found, and post one `count_adjustment` movement. Differences are measured against the stock held *at posting* with balances locked first (movements after the snapshot are not double-counted); gains use the line's cost or the valuation cost, losses the valuation cost; batch items count per batch; serial-tracked items are excluded. Every line must be counted before posting; posted/cancelled counts are frozen by a trigger.
- **Deadlock safety**: every movement first locks all its balance rows in one fixed (warehouse, item) order, then processes outgoing lines before incoming ones; 20 simultaneous opposite-direction transfers all succeeded.

## ADR-17 Sales and GST (Slice 5a: invoices, notes, cancellation)
Decisions you made: **per-line tax rounded to the paisa, invoice rounded to the rupee with a separate round-off line; standard domestic place-of-supply rules plus SEZ/export (with or without payment of tax) and a reverse-charge flag; invoices issue stock directly, credit limit warns only, e-invoice fields reserved**.
- **GST engine** (`gst.ts`) is pure integer arithmetic with no I/O, unit-tested separately. Place of supply: goods = ship-to state, else bill-to, else the supplier's state (counter sale); services = recipient's billing state; exports = 96 (Other Country). Within the supplier's state: CGST+SGST (each half the rate); anywhere else, and always for SEZ and exports: IGST. Each tax component per line is rounded half up to the paisa; the payable total is rounded to the nearest rupee and the difference is a signed round-off posted to a configured account. Tax-inclusive prices (retail MRP) back the tax out of the price. Rates are the item's tax code rate **in force on the invoice date** (Slice 2), recorded per line.
- **Documents**: tax invoice, bill of supply (composition suppliers, tax-free), credit note (returns at the *original* price and *original* tax rate; stock comes back at the *original cost*; serial numbers must be among those invoiced; quantity limited to what is still creditable) and debit note. Numbers come from the per-GST-registration/document-type/financial-year series built in Slice 1.
- **One transaction**: a document number, the stock movement (issue at cost, or return), the journal (receivable with the customer as dimension / revenue / output CGST-SGST-IGST-cess / round-off), the document and its lines, audit and event. A failure (insufficient stock, closed period, missing account) leaves nothing behind, including the number (tested).
- **Immutable documents**: a posted document and its lines cannot be edited or deleted (trigger, any role). The database re-checks the arithmetic at commit: header totals equal the sum of the lines, CGST = SGST, IGST only between states, the grand total reconciles (reverse charge excluded from what is collected). A cancelled invoice keeps its number (cancelled in the allocation ledger, never reused); cancellation reverses the journal and brings stock back at the *exact* value it left at (serials and batches restored), is refused once credit/debit notes exist, and honours period locks. Notes are not cancelled; issue the opposite note.
- **Not built, by design**: delivery challans, e-invoice IRN / e-way bill (columns reserved, nothing reads them), TCS/TDS on sales, composition-scheme *customer* rules beyond treating them as registered, multi-currency sales (base currency only), selling units other than the item's base unit, a draft state for invoices (posting is immediate).

## ADR-18 Quotes and sales orders (Slice 5b)
- **Quotes** are priced by the same engine as invoices (`priceDocument`), so an estimate and the invoice that follows use identical rules; they carry an *estimated* taxable value, tax and total, a validity date, and are immutable except for one transition (`rejected` or `converted`, with the resulting order). Numbers `QT/<FY>/<n>`.
- **Orders** (`ORD/<FY>/<n>`) validate everything an invoice would (registration, customer, items, tax codes, place of supply) when placed, so an order is never un-invoiceable on day one. With `reserveStock` every stocked line reserves its stock through the Slice 4 reservations (same balance-row lock, so two orders cannot promise the last unit; a failing reservation rolls the whole order back, including its number). Order lines are fixed once placed; only `quantity_invoiced` moves, bounded by the ordered quantity.
- **Invoicing an order** goes through the normal invoice posting: tax is recomputed at the *invoice* date (a rate change between order and invoice applies), stock is issued by consuming the line's reservation, and the invoice records the order and line it came from. Orders invoice in parts; `close` stops further invoicing and releases what is still held; `cancel` is only for an order nothing was invoiced against. Cancelling an invoice gives its quantities back to the order (the consumed reservation is not recreated; re-invoicing needs stock to be available).
- Internal document counters share one table with stock documents, so prefixes must never collide (a test caught `SO` being used by both opening stock and orders; orders are `ORD`).

## ADR-19 Receipts and receivables (Slice 5c)
- **The receivable is the general ledger**: receipts and invoices post to the receivables control account with the *customer as the dimension*; there is no second balance to drift. Receipts, credit notes and write-offs are **allocated** to invoices in `receivable_allocations`, and a deferred database constraint refuses to allocate more than an invoice is worth or than a receipt/credit note holds (backstop for concurrent requests, tested with 10 parallel allocations). Allocations are append-only; the only change is a one-time reversal (date + time, so history stays exact); write-offs are journal entries and are final.
- **Money not allocated stays on account** (an advance, shown as a negative customer balance in the receivables account) and can be allocated later; credit notes are allocated the same way. A cancelled receipt (bounced cheque) reverses its journal and releases what it settled; an invoice with money allocated cannot be cancelled until the allocations are reversed.
- **Everything is reportable as of any date** from the immutable documents and the allocation history: customer position (open invoices, unapplied receipts/credit notes, credit-limit flag), statement (opening balance, running balance, cancellations), ageing by days past due (due date = invoice date + the customer's payment terms), and a **reconciliation of documents to the ledger, customer by customer**, which is exercised at five different as-of dates in the tests.
- Write-offs (discounts/bad debts) need a configured expense account and the separate `receivables:writeoff` permission.

## ADR-20 Point of sale and refunds (Slice 5d)
- **A POS sale is a sales invoice plus the receipts taken at the till**, posted in one transaction by composing the invoice engine and the receivables service (no second tax or ledger code path): walk-in customer by default (or a named one), tax-inclusive counter prices by default, stock issued at cost, the payments (which must add up to the invoice total *exactly*) posted as receipts and allocated to the invoice, so the sale leaves a zero receivable. Cash can be tendered above the amount (change is recorded, and only the net amount reaches the ledger). Any failure (payments off by a paisa, an unmapped payment method, insufficient stock) rolls the whole sale back, including the invoice number.
- **A POS return is a credit note plus a refund**: credit note against the counter sale (limited to what was sold, tax-inclusive lines credited tax-inclusive, stock back at the original cost), then the refund paid out by method; the refunds must equal the credit note total. Refunds are a general receivables capability (`POST /v1/receivables/refunds`): pay back an unallocated receipt or unapplied credit note out of a cash/bank account. The database refuses allocations plus refunds above what a receipt or credit note holds; a receipt with a refund cannot be cancelled; position, statement and the ledger reconciliation all account for refunds.
- **Shifts are the cash drawer**: one open shift per terminal (partial unique index), sales/returns only in an open shift, and closing compares counted cash with *opening cash + cash sales - cash refunds* and posts any shortage/overage to the configured cash over/short account (the shift can only be closed once, by trigger). A shift summary reports sales, returns and payments by method.
- Payment methods map to ledger accounts per company (cash -> till account, card/UPI -> bank or clearing account); sell, return, shift and configuration rights are separate permissions (`pos:sell`, `pos:return`, `pos:manage`, `pos:read`).
- A bug the POS tests caught: a credit note against a tax-inclusive line was being computed tax-exclusive (118 instead of 100 + 18). Credit and debit notes now inherit the line's tax-inclusive flag.

## ADR-21 Purchase orders and goods receipts (Slice 6a)
Purchasing is a subledger-composing module like sales: a **goods receipt** (GRN) is one transaction that numbers the document, moves stock in through `StockService.move` at the order's **net price** (price less line discount; stored to 6 places), and accrues **Dr inventory / Cr GRNI** (account 2120, an inventory-control account the posting engine lets only system sources touch). Receipts are immutable; a receipt is never cancelled (stock comes back out through a purchase return, Slice 6b, so inventory cost and GRNI stay in step under WAC and FIFO). Purchase orders touch no ledger; once placed only their status changes and their lines only move `quantity_received` / `quantity_billed` (guard triggers, column-level grants). Receipts may be partial and may run against an order line or with no order (then the unit price is stated); receiving more than the order line's remainder is refused (`receipt_exceeds_order`), enforced under a row lock on the order so concurrent receipts cannot over-receive. Order status (`open → partially_received → received`, or `closed`/`cancelled` by hand) is derived from the stocked lines only; services are billed, never received. Company purchasing settings (payable, GRNI, price-variance, input-tax, reverse-charge accounts and the two match tolerances) are validated by account type/control kind exactly as the sales settings are, and a posting that needs one that is missing fails with a 409 naming it. Internal numbers use prefixes `PO` and `GRN` in the shared per-company/fiscal-year counter table.

## ADR-22 Supplier bills, input tax credit and three-way match (Slice 6b)
A **supplier bill** is one transaction: it checks the match, prices the lines with the GST engine (the same integer arithmetic as sales), takes any non-creditable tax into cost, posts the journal, writes the immutable document, and hands the billed quantities back to the receipts and orders. **Tax direction** is decided by the supplier's state (from the GSTIN, else the billing address, else `supplierStateCode`) against the place of supply (the buyer registration's state unless overridden): same state → CGST + SGST, otherwise IGST; SEZ and overseas suppliers are always IGST. Composition and unregistered suppliers charge no tax unless the buyer pays under **reverse charge**, which posts the tax as a liability (RCM accounts) *and* as credit, and leaves the supplier's payable at the value only. A composition buyer cannot claim credit, and a line flagged `itcEligible: false` takes its tax into cost: on an expense line that is simply a larger expense; on a **stocked** line it is added to the stock's value through the new `StockService.revalue` primitive (below), so the subledger and the GL stay equal. **Journal**: Dr GRNI (the receipt value cleared, plus any non-creditable tax capitalised) · Dr/Cr purchase price variance (bill value less the GRNI cleared, which is also where quantity billed above what was received lands) · Dr input CGST/SGST/IGST/cess (creditable tax) · Dr round-off · Cr payable (supplier as the party dimension) · Cr RCM liability on reverse charge. The last bill against a receipt line clears the *remaining* GRNI value, so rounding never leaves residue. **Three-way match**: a stocked line must bill a receipt line (`receipt_required` otherwise); price is compared with the receipt's net order price and quantity with what is still unbilled, using the company's price % and quantity % tolerances (price deviation counts in both directions). Outside tolerance the bill is refused (409 `match_failed`, listing each issue) until a caller holding `purchasing:approve` resubmits with `overrideMatch.reason`; without the right it is a 403, and a granted override is stored on the bill (approver, reason, time, the issues) and audited as `supplier_bill.match_overridden`. A database check requires an overridden bill to carry its approver and reason. **Returns**: goods returned *after* billing go on a **debit note** (reverses tax at the original rates, stock leaves at its current cost, the difference to the supplier's credit is price variance); goods returned *before* billing are a **receipt return** (stock out, GRNI reduced by the value it was accrued at, difference to price variance). **Cancelling** a bill reverses its journal (and any capitalised tax), gives the quantities back to the receipt and order lines, and frees the supplier invoice number (`supplier_bills_supplier_invoice_unique` is a partial unique index on live bills); a bill with debit notes cannot be cancelled. The payables slice hooks cancellation to refuse bills with money allocated.

**Stock revaluation (`StockService.revalue`)** is a value-only movement (quantity 0, type `revaluation`, prefix `SV`) that adds or removes cost on stock already held. Weighted-average stock takes the share that is still on hand (the average moves); FIFO stock takes it on the receipt's own cost layer (the layer's unit cost changes; a database trigger permits that only in a transaction that also writes a revaluation ledger row for the same item and warehouse). The share that relates to units already sold or used is posted to the cost-variance account instead. Landed cost (6d) uses the same primitive.

## ADR-23 Supplier payments and payables (Slice 6c)
The payable is the **general ledger** (the payables control account, the supplier as the party dimension), exactly as receivables are: bills credit it (Slice 6b), payments and debit notes debit it, refunds received from a supplier credit it. `supplier_payments` records money paid out (Dr payables / Cr the cash or bank account chosen by the caller, which must be an ordinary asset account); `payable_allocations` say which payment or debit note settles which bill (exactly one source, one supplier enforced by composite foreign keys, reversible once, append-only otherwise); `supplier_refunds` record money coming back from an advance or an unapplied debit note. **Commit-time triggers** guarantee that what is allocated to a bill never exceeds its value and that allocations plus refunds drawn from a payment or debit note never exceed what it holds, even under concurrent requests (the application checks first and says why: `exceeds_outstanding`, `exceeds_available`; sources and bills are locked in a fixed order). Cancelling a payment (a bounced cheque) reverses its journal and releases its allocations; it is refused once a refund was taken out of it. Cancelling a bill is refused while money is allocated to it (`has_settlements`). **Reports are computed as of any date** from the immutable documents and the allocation history: supplier position (open bills with days overdue, unapplied payments and debit notes, net balance; positive means we owe), ageing buckets (current, 1-30, 31-60, 61-90, over 90 days past the bill's due date), statement with opening and running balances (cancellations appear on their own date), and a **reconciliation** that proves the documents equal the ledger supplier by supplier at each date.

## ADR-24 Landed cost (Slice 6d)
Freight, customs duty, insurance and handling that were booked as ordinary expenses (a forwarder's bill, a payment) are moved into the cost of the goods they brought in by a **landed cost voucher**. The voucher names the charges (each with the expense account it was booked to), the **receipt lines** they relate to, and a basis (`value` or `quantity`). The total is shared over the receipt lines with `allocateProportionally` (integer arithmetic; largest remainders get the leftover units, so shares always add up to the total to the last 1/10000). Each share goes through `StockService.revalue` (ADR-22): **weighted-average** stock takes the part that is still on hand and the average moves; **FIFO** stock takes it on the receipt's own cost layer; the part that relates to units already sold or used is posted to the **cost-variance account** instead of stock. The revaluation credits a **landed-cost clearing account** (`freightAccountId` in the purchasing settings); a second journal debits the clearing account and credits each charge's own account, so the clearing account nets to nothing and the charge accounts are relieved. Vouchers are immutable; a database trigger checks at commit that charges and allocations both equal the voucher total. **Cancelling** takes the cost back out the same way (negative revaluation) and reverses the charge journal. Internal number prefix `LC`.

## ADR-25 Manufacturing masters (Slice 7a)
Manufacturing is the first industry specialization. **Work centres** carry labour, machine and overhead rates per hour (changed in place, versioned and audited; work orders snapshot the rates when they use them). A **bill of materials** is for an active, stocked semi-finished or finished item; it has a base quantity, lines (component, quantity per base, scrap %) and routing operations (operation number, work centre, setup hours and run hours per base). A BOM is **immutable once created**: a change is a new version (`version` per item, number `BOM/yyzz/nnnnnn`); the only edit is making it obsolete, which frees its date range. For one item, **active BOMs can never overlap in time** (an exclusion constraint, so no application bug can create two). Components must be active, stocked items, never the item itself, never repeated; a loop through other BOMs is refused (`bom_cycle`). **Explosion** turns a target quantity and a date into the multi-level tree and the flat raw requirements, using the BOM in force on that date at each level (component quantity x target / base, grossed up for scrap as quantity / (1 - scrap), rounded half up at six places).

## ADR-26 Work orders and work in progress (Slice 7b)
A **work order** snapshots its BOM: material requirements (component quantity x planned / base, grossed up for scrap) and planned operation hours. It moves planned → released → in progress (on its first transaction) → completed, or planned/released → cancelled; completed and cancelled are final (database trigger). Everything that happens to it is an **append-only transaction carrying its cost**: *material issue* (stock out at actual cost through `StockService.move`, Dr WIP), *material return* (stock back at the order's average cost for that material, Cr WIP), *labour* and *overhead* (hours x the work centre's rates **at the moment of reporting**: labour = labour rate; overhead = machine + overhead rates; Dr WIP / Cr the absorbed accounts), *output* (finished goods into stock at the pooled cost, Cr WIP) and a *residual* clearing. The order's WIP is the sum of its transactions. **Output costing is actual cost**: a report of q units takes the whole WIP pool when q reaches the remaining planned quantity, otherwise pool x q / remaining (so the cost of a partial output depends on what has been put into the order so far); scrap quantity is recorded and its cost stays with the good units. Completing an order clears whatever WIP is left (short output, over-consumption) to the production-variance account. Orders are locked row-wise, so concurrent issues and outputs serialise and cannot lose or invent cost. **WIP reconciliation** proves, as of any date, that the work orders' WIP equals the WIP control account (and the inventory reconciliation now excludes the configured WIP account the same way it excludes GRNI). Number prefix `WO`.

## ADR-27 Costing and production variances (Slice 7c)
Because production is costed at **actual** cost (ADR-26), costing here is analytical and posts nothing. **Roll-up** answers "what should this cost?" on a date: each component is priced at its current stock cost (average of what is on hand across warehouses, else the last known cost; an item with no cost history is reported in `itemsWithoutCost` and the result is flagged incomplete), sub-assemblies by their own BOM in force on that date (multi-level, with scrap), and labour and overhead from the routing hours at the work centres' current rates (setup hours once per run, run hours scaled to the quantity). **Variance** compares a work order's actual cost with its own plan costed at the prices and rates *actually paid*, which isolates what the shop floor controls: *usage variance* per material (net issued less requirement, at the actual average cost) and *efficiency variance* per operation (actual less planned hours, at the actual cost per hour), summing to the order's total variance (positive = cost more than planned), plus yield (produced / planned, scrap rate), unit cost actual vs planned, finished-goods value and the residual cleared to the variance account. A period report lists completed orders (by their last transaction date) with totals. Orders still running can be read too (what has happened so far).

## ADR-28 Subcontracting / job work (Slice 7d)
A **subcontract order** is a work order (ADR-26) whose materials warehouse is the job worker's own location (a warehouse of kind `subcontractor`), plus the subcontractor, the agreed charge per finished unit and the warehouse materials are sent from. The principal keeps owning the materials, so a **delivery challan** is a direct stock transfer between our own warehouses with **no ledger entry**; it records the challan number (`DC/yyzz/nnnnnn`), vehicle and e-way bill number, and the first challan starts a **one-year return clock** (`return_due_date`; GST treats goods not returned or accounted for as a supply). What the job worker still holds for an order is sent less returned less consumed; unused materials come back on a return challan. **Receiving** finished goods is one transaction through the work-order machinery: the materials actually used (default: the BOM requirement for the quantity received; the job worker's reported usage can override, so waste shows up as cost and as usage variance) are issued into WIP from the job worker's warehouse at actual cost; the **job-work charge** (default rate x quantity, or the invoiced amount) is capitalised Dr WIP / Cr a **subcontract clearing account**, which is where the job worker's own supplier bill was booked as an ordinary expense (so GST input credit on job work flows through the normal bill, ADR-22, and the clearing account's balance shows charges billed but not yet received); and the finished goods come into stock taking the **whole pool** (what was consumed and charged for this receipt is exactly what these goods cost). Completion clears any residual to production variance. A pending report lists materials out with days outstanding and an overdue flag after 365 days.

## ADR-29 Financial statements and year-end close (Slice 8a)
The statements follow the structure of **Schedule III (Division I)** in its common simplified form (`schedule3.ts`: balance-sheet and profit-and-loss lines with fixed codes). What is editable is the **mapping of chart accounts to those lines** (`statement_mappings`, validated by account type, with a default mapping for the template chart applied on request). An account nobody mapped is never lost: its balance lands in the "other" line of its kind and is listed in `unmappedAccounts`, so the statements always tie to the ledger. **Profit and loss** is computed for any period (with an optional comparative) from journal lines, leaving out year-end closing entries and their reversals, so a closed year still shows its result. The **balance sheet** as of a date (with an optional comparative) shows profit not yet moved to reserves on its own line, so it balances before and after closing and `balanced` proves it. The **cash flow** is indirect and derived from the movement in balance-sheet lines between two dates; it reports `reconciled` when operating + investing + financing equals the movement in cash. **Year-end close** posts one journal entry dated the last day of the fiscal year that zeroes every income and expense account into the retained-earnings account (a company setting); years close in order, the last period must still be open to take the entry, and `fiscal_year_closings` records it (one live closing per year, enforced by a partial unique index; reopening reverses the entry and is refused while a later year is closed).

## ADR-30 GST returns (Slice 8b)
Returns are **computed on demand** from the immutable sales invoices and supplier bills; nothing is stored or filed, so a return can never disagree with the books. All are per GST registration. **GSTR-1** (month): `b2b` by recipient GSTIN (with SEZ shown as `SEWP`/`SEWOP`), `b2cl` (inter-state B2C invoices above 2.5 lakh, by place of supply), `b2cs` (everything else B2C, summarised by supply type, place of supply and rate), `exp` (with and without payment), `cdnr` and `cdnur` (credit and debit notes), `nil` (zero-tax supplies by registered/unregistered and inter/intra), `hsn` (by HSN, unit and rate; credit notes subtract), and `doc_issue` (number ranges, cancelled and net). An invoice counts in its own month unless it was cancelled on or before that month's end. **GSTR-3B** (month): 3.1 outward taxable (net of credit notes), zero-rated, nil/exempt, inward reverse charge; 3.2 inter-state supplies to unregistered and composition recipients by place of supply; 4 input credit (imports, reverse-charge credit, other), reversals (debit notes), net and blocked credit; and **6 payment**: output tax against input credit using the statutory order (IGST credit first against IGST, then CGST, then SGST; CGST credit against CGST then IGST; SGST credit against SGST then IGST; cess against cess), the remainder payable in cash, reverse-charge tax always in cash, and credit left unused. The **ITC register** lists each bill and debit note with the credit it carries or loses. **CMP-08** (financial-year quarter, `YYYY-Qn`, Q1 = April-June) applies the registration's composition rate (a per-registration setting, `gst_return_settings`) to the quarter's turnover (bills of supply net of credit notes), split equally between central and state tax, and adds reverse-charge tax on inward supplies. A composition registration cannot be asked for GSTR-1/3B, nor a regular one for CMP-08.

## ADR-31 Payroll (Slice 8c)
Payroll covers **employees** and **contract workers** (people on your roll paid directly: monthly, by the day or by the hour; the contractor-agency case is an ordinary supplier bill). **Statutory rules are data, not code**: scalar rates (PF and ESI percentages and wage ceilings, income-tax standard deduction, rebate and cess) and slab sets (income-tax slabs per regime, professional-tax slabs per state) are immutable, effective-dated rows; the rule in force on a date is the latest row on or before it, and a change is a new row, never an edit (`rate_exists`/`slabs_exist` refuse a second rule for the same date). A starting set for 2025-26 can be seeded, but it is a convenience your accountant must confirm. **Pay** comes from an effective-dated, immutable **salary structure** (basic, fixed and percent-of-basic components, flags for taxable / PF wages / ESI wages) plus the month's **inputs** (loss-of-pay days, units worked for daily/hourly people, bonus, other deduction). The calculation (`payroll-calc.ts`) is pure integer arithmetic: loss-of-pay and mid-month joining/leaving prorate by calendar days; PF on PF wages up to the ceiling; ESI (rounded up to the rupee) only while wages are within the ceiling; professional tax from the state's slab; **income tax on salary** projects the year (earned to date plus this month for the months left), applies the standard deduction, slabs, rebate and cess, and spreads what remains after tax already deducted over the months left; contract workers have a flat TDS rate on what they are paid. A **payroll run** for a month calculates everyone, writes the immutable run and payslips (each snapshotting its figures, the structure used and the tax basis), and posts one journal (Dr salaries and the employer's PF/ESI cost; Cr net salary payable, PF, ESI, professional tax, TDS and other-deductions payables) in one transaction; one live run per company and month (database partial unique index). The run refuses to start, listing who and why, when anyone lacks a structure, a required input or a needed statutory rule. A run is **paid** in one go (Dr salary payable / Cr cash or bank) and can be **cancelled only while unpaid and with nothing remitted** (its journal is reversed and the month can be run again). **Remittances** pay PF, ESI, professional tax or TDS for a month and can never exceed what the month's runs deducted; `liabilities` shows what is still owed. Inputs of a month with a live run are frozen.

## ADR-32 POS offline sync (Slice 8d)
A till can sell without a connection and upload later. **Devices** are registered per terminal (`pos_devices`; revocation is final) and uploads need only the `pos:sync` right, so a till's credential can post its own sales but cannot read the books. The till queues sales and returns under **client-generated ids** with the time each happened (an ISO date-time with its offset; the date part, as the till saw it, becomes the document date). `POST /v1/pos/sync/batches` applies the items **in the order they happened** (the till's own order breaks ties, so a return always follows the sale it returns), **each in its own transaction** through the same `PosService` as an online sale, so an offline sale books exactly what an online one does (invoice, stock at cost, receipts, ledger); one bad item never spoils the others. The outcome of each item is stored under (device, client id) with a hash of its content: a repeated upload returns the stored outcome (`duplicate`) and books nothing twice, even when two uploads of the same batch race (a per-item advisory lock serialises them), a reused id with different content is refused (`client_id_reused`), and a rejected item (insufficient stock, closed period, closed shift, payment mismatch, a clock in the future, an invalid payload, a return of a sale not yet uploaded) keeps its reason and can be **retried unchanged** once the cause is fixed. An applied item is final (database trigger). Returns of offline sales name the sale by the till's own id and its lines by line number, since the till cannot know server ids. `GET /v1/pos/sync/catalogue` gives the till what it needs to sell offline (sellable items with HSN and tax code, the tax rates in force today, mapped payment methods, the walk-in customer, its terminal) with an `updatedSince` filter; the rejected queue is listed per device. The till is authoritative for what it sold and at what price.

## ADR-33 Platform hardening (Slice 9a)
Four operational protections, none of which changes the business model. **Retention** (`npm run maintenance:retention`, run on a schedule by the operator) purges only what is operational noise: expired idempotency keys (after a 24 h grace), delivered outbox events and their dispatch/consumed rows (after 30 days; dead letters are kept for investigation) and sessions expired for 180 days. It runs as the migrator role through explicit, role-scoped RLS delete policies (migration 0026) and a guard trigger that lets only that role delete outbox events; the runtime role still has no DELETE anywhere. Audit, accounting, stock and document tables are never purged. **Rate limiting** is a per-instance fixed window per client address (`RATE_LIMIT_PER_WINDOW`, off by default), exempting health probes, answering 429 with `Retry-After`. **Principal cache** (`AUTH_PRINCIPAL_CACHE_TTL_MS`, off by default, at most 60 s) reuses a resolved credential without a database round trip; role/permission changes and key or session revocation made through this API forget the tenant's entries at once. **docs/DEPLOYMENT.md** is the operator's guide.

## ADR-34 Approvals (Slice 9b)
A generic **maker-checker** engine that gates existing commands without changing their endpoints or adding draft states. **Policies** (`approval_policies`) say that, for a document type in a company, an amount at or above a threshold needs N approvals (1-5); several thresholds form tiers and the highest one reached decides. Gated today: purchase orders (value before tax), supplier payments (amount) and manual journals (total debits). **Requests** carry the exact payload, validated by the real endpoint's schema and fixed by a canonical hash. Approvers (`approvals:decide`) approve or reject; nobody may decide their own request (API check plus a database trigger), each approver counts once, a rejection is final. An approved request is valid for the policy's days; the real command (`POST /v1/purchasing/orders`, `/v1/payables/payments`, `/v1/journal-entries`) then needs the `Approval-Id` header, and **consumes** it in its own transaction (row-locked, so concurrent commands cannot both spend it; a command that fails gives it back). The document is linked to the request, and everything is audited and published. Requests and decisions are append-only; the runtime role can only move a request forward through its states.

## ADR-35 Dashboard and bank reconciliation (Slice 9c)
**Dashboard** (`GET /v1/dashboard`, `dashboard:read`) stores nothing: it composes the ledger (cash = accounts mapped to the Schedule III cash line, revenue and expenses excluding year-end closing entries), the receivables and payables ageing, stock value (inventory control accounts), a monthly trend for the fiscal year and counts of what needs attention (pending approvals, unmatched bank lines, open purchase orders and work orders). **Bank reconciliation** designates ordinary asset accounts as bank accounts (`bank_accounts`, with an optional *cleared-through* date for history reconciled before the books were kept here). Statements are imported as immutable documents (balances must add up, no duplicate content, no overlapping periods, void to correct). A statement line is **matched** to one or more ledger lines whose total is exactly its amount; matches are never edited, only ended with a reason, and the database re-checks at commit that every matched line equals its ledger lines to the paisa and that a line's status agrees with its matches. Auto-match pairs only unambiguous lines (same amount, within N days, each the other's only candidate). A bank item the books lack (charges, interest) is **booked** as a journal against a chosen ordinary account and matched in one step. The **reconciliation statement** at a date shows book balance, deposits in transit, outstanding payments, bank items not in the books, ignored items, the expected statement balance and the difference from the bank's closing balance.

## ADR-36 Company setup service (desktop client D1)
`GET /v1/companies/:id/setup/status` lists what a company still lacks before it can invoice (GST registration, location, warehouse, financial year, chart, statement mapping, stock/sales/purchase accounts, number series, GST slabs). `POST /v1/companies/:id/setup/apply-defaults` completes the defaultable ones with the standard Indian setup. It is repeatable and **never overwrites** a value that is already set; each step commits on its own so a failed run resumes where it stopped (it is not one transaction, because each module owns its writes). The recommended account choices live in `setup.service.ts` (`INVENTORY_DEFAULTS`, `SALES_DEFAULTS`, ...), keyed by the codes of the starter chart. The OpenAPI document now also lists path parameters (`addPathParameters`).

## Assumptions to confirm
1. GST registration types: regular, composition, SEZ, casual, non-resident, input-service-distributor, TDS/TCS deductor (check constraint list, easy to change).
2. GSTIN: 15 chars, format regex, state code = first two digits, PAN inside GSTIN must equal the company PAN. State code validity table is not enforced. A GSTIN is unique per tenant.
3. Business location's `gst_registration_id` is nullable (non-GST site); at most one *principal* location per registration.
4. Financial-year default is April–March (company setting, not yet used by any posting).
5. No DELETE privilege for the app role anywhere (soft-state via `active`/effective dates).
6. Warehouse kinds list above.
7. Numbering: the GST financial year is fixed April-March (statutory) and independent of the company's books year; `document_type` is a free `snake_case` string until the document slices define the registry.
8. Permission catalog (`organization`, `users`, `roles`, `api_keys`, `audit`, `numbering` read/write) is a starting set; the only built-in role is Owner. Other roles are tenant-defined.
9. Session lengths: access 15 min, refresh 30 days, lockout 5 failures / 15 min (all configurable).
10. Self-signup is OFF by default; tenants are provisioned by the platform operator.
12. Master data: parties are one table with roles; GST treatments = registered_regular, registered_composition, sez, deemed_export, unregistered, consumer, overseas; one GSTIN per party; a party's state comes from its addresses (not checked against its GSTIN prefix yet).
13. Items: no item categories/groups, brands, variants, barcodes or per-item costing method yet (costing method is decided with the inventory slice). Services are never stocked. Tax code on an item is optional.
14. Tax: only IGST/CGST/SGST/cess percentages (cess ad-valorem only; specific-amount cess and composition-scheme flat rates are not modelled). Permissions `tax:manage` and `pricing:manage` are separate from `masterdata:write`.
15. Price lists: one price per (list, item, unit, minimum quantity, period); customer-specific lists and discounts/schemes are not modelled yet.
16. Accounting: fiscal years are 12 calendar months starting on the 1st (a short first year is not supported); periods are monthly; periods close strictly in order. Reopening needs `accounting:reopen`; locking is irreversible.
17. Entries are in the company's **base currency only**. Foreign-currency postings arrive with the sales/purchase documents (they will carry the foreign amount and rate as memo columns next to base amounts).
18. No draft/approval workflow for manual journals yet (posting is immediate, controlled by period, account and permission rules); no recurring journals, no year-end close / retained-earnings roll-up (the trial balance shows income and expense accounts as they are), no budgets, no dimensions beyond business location and party on a line.
19. `entry_no` is not required to be gapless; a rolled-back posting returns its number, so committed numbers are consecutive in practice.
20. Inventory: valuation is per item per warehouse (not company-wide); one GL account per item *type* (not per item); quantities are in the item's base unit (conversions are applied by documents); no movement reversal yet; no item categories or landed cost yet (purchasing slice).
21. Negative-stock valuation is approximate by nature (shortfalls use the last cost); the subledger and GL still agree because both take the same ledger values.
22. Counts: one adjustment per count; no recount/approval workflow; serial items are checked by serial adjustments instead. Transfers: same company only (inter-company is out of scope), no transport/charges, in-transit stock has no separate GL account (it stays in the item's inventory account).
23. Reservations are by warehouse (and optional batch); no cross-warehouse allocation, no priority/pre-emption, serial items not reservable.
24. Sales: an invoice's place of supply must be one state (mixed goods/services with different places must be split into two invoices); selling unit = the item's base unit; a bill of supply applies no tax at all; regular supplier + bill of supply is allowed and tax-free (you confirm when that is legally right); only regular, composition and SEZ registrations issue sales documents.
25. Receivables are tracked as journal lines with the customer as a dimension on the receivables control account; allocation of receipts and ageing arrive in 5c.
26. Orders: one price per line fixed at order time (price lists are not auto-applied yet); no delivery scheduling/partial shipments separate from invoicing; serial-tracked lines choose their serial numbers when invoiced, not at order time; no order amendment (cancel/close and re-enter).
27. Receivables: advances sit in the receivables control account (no separate customer-advances liability); no TDS/TCS deducted by customers on receipts; no multi-currency receipts; no dunning, interest on late payment or payment-gateway integration; receipts are allocated by invoice (not by line).
28. POS: exact payment at the counter (no credit sales or partial payment in POS); one currency; no loyalty, coupons, price overrides or manager approval workflow; no offline mode (the API is online-only; offline sync is a separately designed later slice); cash drawer counts only cash (no blind count, denominations, safe drops or paid-ins/outs); a return needs the original counter sale (no receipt-less returns).
29. Purchasing (6a): a purchase order has no tax or totals of its own (the supplier bill decides tax, place of supply and eligibility); one price per line fixed at order time; no order amendment (cancel/close and re-enter) and no approval workflow on orders; over-receipt is blocked rather than tolerated (the receipt tolerance applies to billing); a receipt is valued at the order's net price, so any price difference appears on the bill as purchase price variance; unordered receipts are allowed and valued at the price stated; no quality inspection/quarantine step, no supplier delivery scheduling, no multi-currency purchasing.
30. Bills (6b): the match tolerance is applied to the *absolute* price deviation (a bill cheaper than the order by more than the tolerance is also held), and to quantity only when billing more than what is still unbilled on the receipt (or, for service lines, on the order). Stocked items are always billed through a receipt line; a purchase with no goods receipt first is not possible for stock (receive it unordered, then bill it). Supplier bills are not numbered per GST registration (purchases have no statutory sequence): the internal number is `BILL/yyzz/nnnnnn`, debit notes `PDN/…`, returns of unbilled goods `PRET/…`. The buyer-side debit note is an internal document; the supplier's own credit note (for GST adjustment) is entered as a bill against the original with negative effect in a later slice, not here.
31. Bills (6b): no TDS/TCS on supplier payments, no import duties or bill of entry for overseas suppliers (an overseas bill is IGST at the item's rate), no ITC time limits or 2B reconciliation, no blocked-credit rules beyond the per-line flag, no multi-currency bills, no tax-inclusive correction on reverse-charge tax, no landed cost yet (6d).
32. Revaluation: non-creditable tax capitalised on a weighted-average item spreads over everything on hand (the average moves for all units); a FIFO item takes it on the receipt's layer; units already consumed take their share to the cost-variance account (required when a bill capitalises tax on stock).
33. Payables (6c): an advance paid to a supplier sits in the payables control account (no separate supplier-advances asset); no TDS deduction on payment, no payment batches, bank files or approval workflow, no early-payment discount, no write-off of small balances (a debit note or a refund settles them), no multi-currency payments, no cheque register; a payment is allocated by bill, not by line; the bill's due date comes from the supplier's payment terms (none: due on the bill date).
34. Landed cost (6d): charges are booked as expenses first and relieved by the voucher (the voucher never creates a payable); allocation is by booked value or by quantity only (no weight or volume, which items do not carry yet); the whole kept quantity of a receipt line takes a share (returned units excluded); no landed cost on stock transferred away from the receiving warehouse (the share is taken on the receiving warehouse's stock only, and the rest of it goes to cost variance); no automatic landed cost from a supplier bill; no revaluation of cost already issued to customers.
35. Manufacturing (7a): one BOM per item per period (no alternates, co-products or by-products yet); scrap is a per-line percentage of the requirement (not yield loss of the whole batch); routing is linear (no parallel operations, no operation dependencies); operation hours are per BOM base quantity; no engineering change orders beyond a new version.
36. Work orders (7b): materials may be over-issued beyond the requirement (recorded; usage variance is a 7c report); issues are by item at a warehouse the caller names (no lot-level reservation, no backflush); one finished item per order (no co-products or by-products); output in partial quantities is costed on the pool so far (an average of what the order has absorbed), which is exact only once the order is complete; scrap has no GL entry of its own; labour hours are not tied to employees or payroll; machine and overhead rates are both absorbed into the overhead account; a completed order cannot be reopened.
37. Costing (7c): there are no standard costs and no price variance (materials are bought at whatever the purchase cost; purchase price variance is a purchasing concept, ADR-22); the roll-up uses *current* average stock cost, not a frozen standard; operations with no recorded hours are planned at the work centre's current combined rate; variance percentages are shown to four decimals and omitted where the plan is zero.
38. Subcontracting (7d): the job worker's invoice is booked as an ordinary supplier bill to the clearing account and is not matched automatically to receipts (the clearing account balance is the reconciliation); GST on the job-work charge and on challans (ITC-04 reporting, capital goods three-year rule, GST on goods not returned within the year) is not automated: only the one-year deadline is tracked; one job worker per order; materials are consumed at receipt, not as the job worker uses them; the job worker's location is a plain warehouse with no separate address or GSTIN; no rework, no returning finished goods, no sending semi-finished goods on to a second job worker in one order (use two orders).
39. Statements (8a): Schedule III is applied in its simplified common form (no notes to accounts, no ageing schedules, no related-party disclosures); tax expense is whatever accounts you map to the tax line (no deferred tax computation); finance cost stays inside operating cash flow; perpetual inventory means cost of materials consumed is cost of goods sold (no opening/closing stock reconciliation line); statements are per company (no consolidation) and in the company currency.
40. GST returns (8b): the JSON follows the portal's section and field names but is not a filing file (no portal upload, no signatures, no 2B reconciliation, no amendments tables 9A/9C, no e-invoice IRN/e-way data beyond what documents carry); each month is computed independently (no electronic credit ledger or cash ledger carried between months, so unused credit is reported but not applied next month); outward supplies where the recipient pays tax under reverse charge are shown informationally and carry no liability; non-GST outward supplies and ISD/Rule 42/43 reversals are always zero; imports are recognised by an overseas supplier (goods and services are not told apart); CMP-08 uses one rate for the whole turnover and GSTR-4 (the annual composition return) is not produced; GSTR-9 annual return is not produced; interest and late fee are not computed.
41. Payroll (8c): salary is processed monthly on calendar-day proration (no 26-day or 30-day conventions); a structure revision applies from the month it starts (the structure in force on the first day of employment in the month is used); PF is employee 12% plus employer 12% in one liability (no EPS/EPF split, no admin or EDLI charges, no voluntary PF); ESI contribution periods are not tracked (a person stays covered for the month their wages are within the ceiling); professional tax has no February adjustment; income tax on salary ignores other income, deductions under the old regime (80C etc.), HRA exemption, arrears and previous-employer income, and the new-regime slabs are the 2025-26 ones; Form 16/24Q, PF ECR, ESI and PT return files are not produced; leave is only the loss-of-pay days you enter (no leave balances, holidays or shifts); no overtime rules, gratuity, bonus-act or full-and-final settlement; contract-worker TDS is a single flat rate; salaries are paid per run, not per person; employee numbers are `EMP-nnnnnn` and `CWK-nnnnnn`, independent of the financial year.
42. POS sync (8d): a device is trusted by its registration and the credential it uses (it is not cryptographically bound to one API key); there is no limit on how long a till may stay offline, but sales into a period that was closed meanwhile are rejected for manual handling (reopen the period or enter the sale by hand), as are sales whose shift has been closed; prices and discounts are taken as the till sent them (no server-side re-pricing or conflict with newer price lists); stock is checked when the item is applied, so an offline sale of stock that has meanwhile gone is rejected rather than allowed to go negative; the catalogue carries items and tax rates but not price lists, serial numbers, batches or customers other than the walk-in; no push notifications to tills, no device-level conflict merge for other documents (only sales and returns sync).
43. Rate limiting (9a) is in memory per instance (N instances allow N times the limit; use the edge proxy/WAF for a global limit) and keys on the socket address Fastify/Node reports; behind a load balancer every client looks the same until trust-proxy handling is configured, so enable it at the proxy first.
44. Principal cache (9a): a revocation made directly in the database (not through the API) or on another instance takes effect after at most the configured TTL; leave it at 0 if that bound is unacceptable.
45. Retention (9a): the audit log is never purged by the application; archiving or partitioning it is an infrastructure decision. The migrator role doubles as the maintenance identity; use a separate role with the same two policies if you prefer.
46. Approvals (9b): approval is decided by permission (`approvals:decide`), not by reporting line, role or per-person limit, and applies tenant-wide; segregation of duties is strict (the requester can never approve, so a one-person tenant should configure no policy); an approval is bound to the exact payload (any change, even of one paisa, needs a new request) and is single use; thresholds compare the pre-tax order value, the payment amount and the journal's total debits; a policy raised after approval invalidates older approvals that had fewer approvals; no escalation, delegation, e-mail or push notification, and no gating yet of bills, receipts, stock adjustments, payroll runs or period closes (add a document type to `modules/approvals/subjects.ts` to cover them).
47. Dashboard (9c): figures are as of the requested date inside the fiscal year that contains it (default today); the profit and loss part is one consistent snapshot but receivables and payables are read a moment later; "revenue" is every income-type account and "expenses" every expense-type account (so tax expense and other income are included; unmapped accounts still count); there is no budget, target or forecast, no per-branch split and no stored KPI history.
48. Bank reconciliation (9c): statements are entered as data (no bank-file parsing, bank feed or CSV/OFX/MT940 import; do that in the client); amounts are signed (money in positive); the reconciliation is as of a date and uses the latest active statement ending on or before it; a ledger line counts as cleared only when matched to a statement line dated on or before the date; ledger lines on or before the account's cleared-through date are treated as reconciled earlier, and an opening check compares the first statement's opening balance with the books at that date; reconciliation does not lock periods or ledger lines, so a matched ledger line can still be reversed (the reversal then appears as a new unmatched line); foreign-currency bank accounts are not supported (single currency); bank charges booked from a statement line are posted as ordinary journals and are not subject to approval policies.
49. Clients (desktop client D0): browser-style clients are allowed only from origins listed in `CORS_ALLOWED_ORIGINS` (exact match, no wildcard, credentials are bearer tokens not cookies); `GET /v1/meta` is public and reveals only the product name, API version and enabled sign-in modes. The OpenAPI document describes request bodies but not yet query parameters or responses; clients validate responses themselves (backend gap G8).
50. Setup defaults (D1): semi-finished goods are held in the finished-goods inventory account until mapped elsewhere; sales write-offs and round-off use "Other expenses" (5900); freight uses "Manufacturing overheads" (5220) and cost variances use "Inventory adjustments" (5300); number series are INV, BOS, CN, DN with the financial year, 5-digit padding, starting at 1, for every active GST registration and every financial year that exists; GST slabs 0, 5, 12, 18 and 28 per cent plus Exempt and Nil-rated are created with rates effective from the first day of the earliest financial year; cess, TDS/TCS, manufacturing and payroll accounts are not configured by this endpoint; the starter chart is the only template (`manufacturing_india`), so a company with a custom chart gets "blocked" messages for accounts it lacks.
51. List search (D2): `q` on items matches the code from its start or the name anywhere; on parties it matches the code or GSTIN from the start and the legal or trade name anywhere (case-insensitive, wildcards literal). There is no trigram index (the migrator role cannot create extensions), so a very large catalogue (hundreds of thousands of rows) may want one added by the database administrator.
52. Invoice calculation (D3): `POST /v1/sales/invoices/calculate` runs the same pricing code as posting (`priceDocument`) in a read-only transaction, so the totals on screen equal the posted invoice; it numbers, reserves and writes nothing, and does not check stock levels (that happens at posting). It needs `sales:post`. Quotes, orders, purchase documents and POS carts are not covered by it yet.
53. Bill preview (D4): `POST /v1/purchasing/bills/preview` runs the real posting (tax, input credit, three-way match, stock revaluation) inside a transaction that is rolled back, so figures and match status equal what posting gives and nothing persists (no number, entry or stock change). It takes the same row locks as posting for its short life, and database checks that run only at commit do not run; it is meant for an explicit "Check bill" action, not for every keystroke. A bill outside tolerance is refused with `match_failed` and its issues, exactly as posting would refuse it; an approver may preview with an override reason.
11. Retention (superseded in part by 9a, see 45): nothing is ever deleted by the runtime role (no DELETE grants), so sessions, idempotency keys, outbox and audit rows accumulate; archival/partitioning needs a separate maintenance role and a retention policy you must decide.

54. Retail catalogue (R1): a category is a tree with a no-discount rule that applies to the category and everything below it; an item has at most one category, a free-text brand and an optional MRP (tax-inclusive, as printed). A barcode is an alias for one item, unique per business ignoring case, and is only ever switched on or off (it is never edited or deleted, so a printed barcode cannot be re-pointed silently). The counter's lookup tries an active barcode first and then the item code. The server does not enforce the no-discount rule on a sale (the till honours it and the catalogue carries the flag); selling at MRP is a counter convention, not a server rule. Variants (size/colour) are not modelled: each variant is its own item with its own barcode.

55. Expenses (R2): an expense voucher books Dr the category's expense account, Cr a cash or bank account, in full (no tax is split out and no input credit is claimed: a bill that carries GST input credit belongs in purchasing as a supplier bill). Vouchers are numbered per fiscal year (`EXP/2526/000001`), never edited, and cancelled by reversing the journal. New permissions: `expenses:read`, `expenses:post`, `expenses:cancel`, `expenses:manage` (categories).
56. Customer wallet (R3): store credit is the customer's unapplied credit in receivables (advance receipts and credit notes), consumed through the normal allocation path; a return can be refunded "to store credit", which leaves the credit note unapplied instead of paying money out. Loyalty points are an immutable ledger per customer; the earn rate and the rupee value of a point are company settings (`retail_settings`), nothing is earned or redeemed until set. Coupons are eligibility rules plus use counts (percent or fixed, minimum bill measured on the pre-discount gross, validity dates, use limit). Points and coupon discounts are applied by the till; the server verifies the right to them (balance, eligibility, limits), records the use and does not recompute the discount. The walk-in customer cannot hold a wallet. Wallet uses on a sale are kept in `pos_wallet_uses`. Assumption to confirm with the accountant: the accounting treatment of loyalty cost (currently none: a redemption is a till discount). New permissions: `retail:read`, `retail:manage`.
57. Counter staff (R4): any user can set a 4 to 8 digit counter PIN (argon2id hashed); holders of `pos:approve` who have a PIN can approve a discount at the till. A company limit (`retail_settings.max_discount_without_approval`, empty = no limit) is checked server-side against the highest line discount sent with a sale, including any extra discount the till adds for points or a coupon; above it the sale needs the approver's user and PIN, which are re-checked inside the sale and recorded in `pos_sale_approvals`. Five wrong PINs lock that approver for 15 minutes. Each line can carry a salesperson (`pos_sale_staff`) for commission and sales reports; no commission is calculated here. Offline sales cannot carry an approval, so a discount over the limit is refused when such a sale syncs. Assumptions to confirm: the limit is a single company-wide percentage and a manager approves per sale, not per line. New permission: `pos:approve`.
58. Licences (deployment sprint 1): what a client has bought is a row in `tenant_entitlements` (plan, modules, numeric limits, optional expiry with a grace period, a read-only switch); a tenant with no row is unrestricted so existing tenants and development databases keep working. Modules are Core (always on: sign-in, users, organisation, master data, the ledger engine, audit) and sales, purchasing, inventory, pos (includes retail and expenses), accounting (the journal, period and statement screens and endpoints only, the ledger itself stays on), gst, banking, approvals, manufacturing, payroll and extras; a module needs others (pos needs sales and inventory, gst needs sales and accounting, banking and payroll need accounting, manufacturing needs inventory), checked when a licence is set. Enforcement is in `AuthGuard` after permissions: `@RequiresModule` on a controller or route (any listed module is enough; a route with none is Core), so permissions and licences both have to allow a request; suspended, or expired past its grace period, means read-only (reads and `/v1/auth/*` still work, so people can view, export and sign out). Limits (users, companies, locations, terminals) are checked inside the creating transaction. The licence reaches the principal in the existing single authentication query, so it adds no round trip. The platform sets it with `PUT /v1/platform/tenants/:id/entitlements`, or a site imports a licence signed by the control plane (`POST /v1/platform/tenants/:id/licence`, Ed25519 over canonical JSON, bound to the tenant, verified with `LICENCE_PUBLIC_KEY`; `npm run licence` makes keys and signs). `/v1/auth/me` returns the entitlements so the app can hide what is not licensed, and `/v1/meta` returns `minClientVersion` so old apps are asked to update. Assumption to confirm: expiry never deletes data and never blocks reading or exporting.
59. Site identity (deployment sprint 2): a client may later run several sites (head office, branches, factory), so records now remember where they were made without changing anything for single-site clients. `erp.sites` lists a tenant's sites (code, name, a number-series code of one or two capital letters or digits, at most one primary); a NULL `site_id` on a record means the primary site, so existing rows are not rewritten. Eighteen tables (the main documents, journal entries, stock movements, POS shifts and sales, the audit log, the outbox and number series) gained a nullable `site_id` whose default is `erp.current_site_id()`: the setting `app.site_id` that each pooled connection carries when the server is started with `SITE_ID` (the site this server runs at), or NULL when it has none, as in single-site and shared-cloud deployments. Internal document numbers add the site's series code to the prefix (`QT` at the primary site, `QTB` at site B), and statutory GST invoice series are per site as well as per registration, year and type (`number_series.site_id`, with a unique index that treats NULL as the primary site), so two sites can never issue the same number; a site with no series of its own cannot invoice until one is created. Sites are managed at `/v1/sites` (`organization:read` and `organization:write`); a licence limit `sites` counts the primary site as one. Not decided here (later, with multi-site and sync): which site owns which master data, and how records move between sites. Assumption to confirm: GST invoice series per site need the same GSTIN, so a client whose branches have separate GST registrations keeps using one series per registration as today.

60. Platform operations (super admin dashboard): the control plane shows every tenant across every cell from what each cell's agent reports (tenant list with usage, licence, and daily validation results) and sends back only three kinds of request: `validate`, `suspend` and `reactivate`, run by the agent against the product's `/v1/platform` API with the platform token (the control plane never holds a database or platform credential). Validation checks are read-only: tenant active, owner exists, ledger balanced, entries match lines, current fiscal year, current-year tax-invoice series per active GST registration, licence modules, licence expiry; a check that cannot run is reported as a failure. A tenant's health is the worst of its cell's health, its failed checks, a stale (over 3 days) validation, being at its user limit and being suspended. Suspension blocks sign-in for the tenant but deletes nothing; it is audited with a reason. "Records" on the dashboard are usage counts (users, companies, documents and events in 30 days), not business data: the control plane never receives ledger or party data. Staff roles: viewer reads, support may request validations and support sessions, admin issues licences and suspends. Licences are issued per tenant and reach the cell on its next visit.

61. Owner web dashboard: `GET /owner` is a single static page served by the product's own server (public, no data in it, strict content policy, never cached) that signs in through `/v1/auth/login` and reads `/v1/dashboard` and `/v1/receivables/ageing` with the owner's own token, so it shows exactly what that user's permissions allow (`dashboard:read`; the debtors list is simply empty without `receivables:read`). Because it is the product's own origin it works on the local network and, through the gateway (which allows only `/owner` besides `/v1/*`), from anywhere, with no CORS and no copy of data outside the cell. Tokens live in the browser tab (session storage) and refresh once on a 401. It is read-only: no posting from the web page. A date with no fiscal year shows a plain message.

62. Remote access rules: each site carries rules for its remote users, set by an admin in the control plane and enforced by the gateway on every request (the product itself does not see them, so on the local network nothing changes). A rule set is a mode (`full`; `readonly`, where only reads and sign-in/refresh/sign-out pass, so the few read-only POST helpers such as invoice calculation are blocked too; `owner_only`, where only the `/owner` page and the dashboard reads pass), an optional list of allowed networks (IPv4 or IPv6, a single address or CIDR; the address is the one the gateway sees, so the gateway must sit behind a proxy it trusts), optional allowed days and hours in a named time zone (a window that runs past midnight belongs to the day it started), and an optional per-site request rate that can only lower the gateway's own limit. Rules reach the gateway with the site's verification and are re-read every minute; people already connected are limited from their next request. A site whose stored rules the gateway cannot read is paused, not left open. `/health/live` is never limited. These rules narrow access; they do not replace sign-in, permissions or the licence. Cells are independent deployments (on-premises servers, dedicated and pooled cloud), each running its own product server, its own owner dashboard page and its own agent; the rules, addresses and on/off switches for all of them live in the control plane and are managed from the super admin dashboard: one list across every cell (with the tunnel state each agent reports) and a bulk apply for an admin, all-or-nothing and audited per cell. Addresses are set per cell, never in bulk.

63. Editions (product tiers): we sell four starting points, listed once in `control-plane/src/plans.ts` and used to pre-fill a licence: **Starter** (small shops: sales, inventory, POS; 3 users, 1 company and location, 2 terminals), **Growth** (adds purchasing, accounting screens, GST returns, banking, expenses), **Enterprise** (adds approvals and payroll; more users, companies and locations) and **Manufacturing** (everything, plus production). A licence is still modules plus limits, so any client can be adjusted individually; an edition is only the starting point, each includes the one below it, and a test keeps them valid. The books (ledger) are always on under every edition: `accounting` licenses the screens and reports, so a Starter shop gets correct GST, stock and sales postings without seeing an accounting screen. The desktop app works out the edition from the licensed modules (never the plan's name): for Starter it opens on the billing counter, shows a short menu (no buying, accounts, payroll or production; advanced pages such as tax codes, units, batches, valuation, transfers, API keys and the audit log are left out of the menu but still work if opened), calls the Accounting group "Expenses" and shows a plain dashboard (cash, sales, what customers owe, stock). Unrestricted businesses see everything.

64. Offline counter (local-first selling): the counter never asks the server to find an item. Each counter keeps the item list (codes, names, barcodes, tax code, MRP, no-discount flag) in IndexedDB on its own computer, downloads it once, then asks only for what changed since the last update (`updatedSince`; every five minutes, when the connection returns, and on request), with one full refresh a day so withdrawn items disappear. Typing and scanning search that local list (barcode, then code, then name words), so the server is asked only for an item that is not on the list (a very new one) and only when there is a connection. A manager's counter registers itself as a device on first opening so offline selling needs no setup; a counter without `pos:manage` shows who to ask. For opening with no connection, the company, registrations, locations, terminal, open shift, price lists and prices are also kept on disk (nothing else is: no customers, invoices or reports) and erased on sign-out, and the app can start from the identity the server last confirmed (kept in the OS keychain, valid 14 days, only on the computer that remembered the sign-in): it shows an offline notice, lets the counter sell, queues sales as before, and confirms the sign-in with the server as soon as it can (a refused sign-in then returns to the sign-in screen). Batch- and serial-tracked items are still sold online only. A half-typed or non-numeric field is treated as empty in every counter calculation, never as an error.

## Deferred on purpose (later slices, not decided here)
Ledgers and posting (immutable, double-entry, period locks, inventory subledger reconciliation); effective-dated tax rules;
document numbering per GST registration and financial year (cancelled numbers preserved, no global gapless counter); offline-sync conflict rules (aggregates already carry `version`/`updated_at`); vendor telemetry (not wired).
The legacy `server/` directory is untouched.
