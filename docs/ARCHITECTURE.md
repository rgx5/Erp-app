# Architecture

OneSyncERP is an Expo / React Native app (TypeScript, strict). One codebase builds the Android and iOS apps; the same
code also runs on the web, which is how the UI is previewed and screenshot-tested in CI-less environments.

```
 ┌──────────────────────────── src/app ─────────────────────────────┐
 │  Expo Router screens (file = route). Thin: read state, call ops.  │
 ├──────────────────────────── src/ui, src/features ─────────────────┤
 │  Design system (OneSync) + reusable flows (pickers, sheets, scanner) │
 ├──────────────────────────── src/data ─────────────────────────────┤
 │  store (zustand) ── ops (state → Changes) ── storage ── sync      │
 ├──────────────────────────── src/domain ───────────────────────────┤
 │  Pure TypeScript: money, tax, pricing, returns, analytics, receipts│
 ├──────────────────────────── src/industries ───────────────────────┤
 │  Industry packs: vocabulary, tax defaults, categories, demo data  │
 └───────────────────────────────────────────────────────────────────┘
```

Dependencies only point downwards. `src/domain` and `src/industries` import nothing from React or Expo, so they run
under plain Node and are tested there.

## Why this stack

* **One team, two stores.** React Native + Expo gives native Android and iOS builds (EAS Build) from one TypeScript
  codebase, camera barcode scanning, biometrics, secure storage, SQLite and print/share — all first-party modules.
* **The business logic is already TypeScript.** The Krishna Collection billing app (the reference product) is a
  TypeScript/React app. Its money, GST, return and report maths were ported verbatim into `src/domain`, so the
  numbers on a phone match the web/desktop product to the paisa.
* **Expo Router** gives file-based routes, deep links (`kosh://`) and a native stack/tab model with no extra wiring.

## Domain layer (`src/domain`)

Pure functions over plain data. Highlights:

| Module | What it does |
| --- | --- |
| `money`, `qty` | Rounding (`round2`, `round3`), Indian digit grouping, amount-in-words, units incl. fractional (kg, m, l…) |
| `tax`, `cart`, `figures` | GST slabs / flat rates, inclusive vs exclusive pricing, line + bill discounts, CGST/SGST split, round-off |
| `returns` | Return planning that reverses exactly what was charged (tax, discount share, loyalty, credit) |
| `checkout` | Payment settling, tender suggestions, loyalty points |
| `analytics` | Dashboard, sales/GST/profit/item/staff reports, day-close figures |
| `stock`, `catalog` | Stock levels, reorder suggestions, counts, roll-ups for the catalogue list |
| `receipt`, `labels` | Receipt/invoice HTML + text, barcode label sheets (EAN-13 / Code 128) |
| `permissions` | Owner / manager / cashier matrix — identical to the server's |
| `types` | Wire-compatible types: a server snapshot hydrates straight into the app |

**Parity is tested, not asserted.** `src/domain/__tests__/krishna-parity.test.ts` replays 2,000+ inputs captured from
the reference implementation (`fixtures/krishna-golden.json.gz`, generated by `scripts/gen-golden.ts`) and requires
identical output.

## Data layer (`src/data`)

```
 screen ──perform(fn)──▶ store.commit(Changes) ──▶ in-memory state (zustand)
                              │                      ▲
                              ├─ write-through ──▶ storage (SQLite / localStorage)
                              └─ outbox (connected workspaces) ──▶ sync engine ──▶ server
```

* **State** — `DataState` is a map per collection (`products`, `variants`, `bills`, …). `Changes` is a
  `{ store, put, del, outbox }` delta; `applyChanges` is pure.
* **Ops** (`ops.ts`) — every business action (`saveBill`, `processReturn`, `receivePurchase`, `adjustStock`,
  `createItem`, …) is a pure function `(state, input, ctx) → Changes`. They enforce the rules (stock can't go
  negative, a held bill can't be edited by a cashier, …), throw `OpError` with a human message, and describe the
  server writes to queue. Screens never mutate state directly.
* **Store** (`store.ts`) — `perform(fn)` runs an op against the current state, applies the delta synchronously for
  the UI, and queues persistence through a serialized batch writer so a crash can never leave half a transaction.
* **Storage** — `expo-sqlite` on devices (a `docs` table keyed by collection + id, plus `kv`; WAL mode),
  `localStorage` on web. Secrets (tokens, PIN salts) live in `expo-secure-store`.
* **Workspaces** — a phone holds one workspace:
  * `local` — the business lives on the phone (offline / trial / demo). Staff PINs are salted hashes on-device.
  * `remote` — the business lives on the client's server; the phone keeps a cached copy and syncs.

## Sync (`sync.ts`, `api.ts`, `runtime.ts`)

Remote workspaces are **offline-first**: every change applies locally at once and is appended to an ordered outbox.

* The engine flushes the outbox in order, one entity per endpoint (see [API-CONTRACT.md](./API-CONTRACT.md)).
* `409 Conflict` counts as done — except for bills, where the engine `GET`s the bill to verify that the conflicting
  record is *this* bill and not another device that took the same number.
* Permanent errors (400/403/404/…) are retried 3× and then **set aside** so one bad record can't block the queue; the
  Sync screen shows them with a retry button.
* What goes over the wire can differ from what the phone keeps: `src/data/wire.ts` swaps empty variant options for `-` (the server
  refuses empty ones) and back again on download.
* The tokens refresh when under 3 h of life remain. A snapshot pull happens only when nothing is pending, and keeps
  held bills and the local audit log.
* `runtime.ts` wires it to NetInfo and AppState (sync on reconnect, on foreground, after every change).

### Multi-device safety

Krishna's protocol assumes one counter per store. A phone is another counter, so connected phones never touch the
store's `nextInvoiceNo`. They number documents from a **device series** (`INV-M4X-0001`, `CN-M4X-0001`, GRNs likewise)
and generate barcodes from a per-device base, so two phones — or a phone and the web till — can never collide.

## Industry packs (`src/industries`)

A pack is data, not code: vocabulary (`Item`→`Medicine`, `Customer`→`Patient`), GST slabs and whether prices include
tax, starting categories with how each is sold (unit, fractional, HSN, GST rate, stock tracking, variants), settings
defaults, expense categories, stock/return reasons and demo data. See [INDUSTRIES.md](./INDUSTRIES.md) to add one.

## Security model

* Roles gate screens in the UI **and** are enforced independently by the server (the app is not the only line of
  defence).
* App lock: optional biometric/device-credential gate when returning from the background.
* PINs: local staff PINs are stored as `sha256$salt$hash`. After 5 wrong PINs the phone locks for 30 s, doubling per
  further miss up to 15 min; the lock survives an app restart.
* Access tokens in secure storage; the outbox strips staff PINs from queued payloads once uploaded.

## Testing & verification

| Check | Command |
| --- | --- |
| Types | `npm run typecheck` |
| Unit/integration tests (Node) | `npm test` — domain parity, ops, store, sync engine, demo invariants |
| Bundles | `npm run bundle:check` (Android + iOS Hermes bundles) |
| Lint | `npm run lint` |

Sync is tested against an in-memory fake server (`src/data/__tests__/sync.test.ts`), including the failure modes:
offline, an expired token (401), a 409 on a bill that belongs to another device, permanent rejection, concurrent flushes
and a pull racing a new sale.
