1. Executive summary

Most of your clients want the system on their own premises, and they ask for remote use. That makes the on-premise server the system of record and the cloud a supporting layer that protects the data, provides remote access, and gives you control over a fleet of 20 to 30 (later more) servers. The plan rests on five ideas.

1. The site is the source of truth. Each client's server holds their database and runs the full application on their local network. If the internet or your cloud is down, the office keeps working. The cloud never sits in the daily path.
2. Hybrid in three levels, built in this order of value. A. Continuous protected backup: every change is shipped, encrypted, to your cloud, so a lost server is recoverable to within minutes. C. Remote access: owners and staff use the product from anywhere through a secure outbound tunnel and a cloud gateway; nothing is copied, so there are no sync conflicts. B. Live standby: a ready cloud copy for read-only reports and for fast failover if the site server fails. Two-way editing of the same data on both sides is deliberately deferred.
3. A fleet agent on every site. A small, signed agent reports health, applies signed updates in a maintenance window with an automatic backup first and automatic rollback, and opens support access only when the client approves. Without this, 30 sites become 30 different problems.
4. One codebase, one build, entitlements per client. The same images run on a client's server, in a dedicated cloud stack, or in a small shared cloud cell. What differs is placement and what is switched on, never the code.
5. Honest commitments. A single VPS provider supports about 99.5% for the cloud services. We sell data-loss and recovery targets that we can prove in drills, expressed separately for what we control (cloud, software, backups) and what the client controls (server hardware, power, local network).

Uptime, data-loss and recovery figures in this document are internal targets (see the decision log, item 12).

5. Reference architecture

5.1 Principles

  • The site works alone. Everything needed to run the business is on the site server. Cloud failures degrade extras (remote access, dashboards), not daily work.
  • Single writer. At any moment exactly one database accepts writes for a client. This is what keeps the books correct, and it is why two-way sync is postponed.
  • Outbound only. The site opens connections to the cloud; no inbound ports on the client's router.
  • Same artefacts everywhere. The images installed at a site, in a dedicated cloud stack and in the shared cell are the same, signed builds.
  • Everything is a fleet item. Each site has a record in the control plane: version, licence, modules, health, backup age, tunnel state, maintenance window.

5.2 Control plane (what it holds)

A small service on the cloud side with its own database and staff-only access. It stores no business data, only site and tenant metadata, signed licences, release channels, heartbeat history, support-session logs and usage counts. If it is unreachable, sites keep running on their cached, signed licence.

6. Hybrid data protection and remote access

6.1 Level A: continuous protected backup (every site)

ItemDesign
What is capturedPostgreSQL write-ahead log segments shipped continuously (a new segment is forced at least every 60 to 300 seconds), plus a full base backup nightly and an incremental in between. This gives point-in-time recovery to any second after the last shipped segment.
ToolingA purpose-built PostgreSQL backup tool (pgBackRest or WAL-G) with compression, parallel transfer, integrity checks and retention. Assumption: pgBackRest, to be confirmed in a proof of concept.
EncryptionEncrypted on the site before leaving it, with a key per client. The cloud holds ciphertext only. Recovery keys are held by you, in your vault, under dual control (decided), so a lost server never means lost backups. A client copy is only provided if a contract says so.
Destinations1) the backup repository on your Hostinger side; 2) a second copy in an off-provider bucket; 3) a local backup disk at the site (three copies, two media, one off-site).
Protection from tamperingThe site's upload credentials can add data but not delete it; deletion and retention run only from the cloud side. Ransomware on a client's network cannot erase the cloud copies.
If the internet is downWAL queues on the site disk. A cap on queued WAL and a disk-usage alert protect the server from filling its disk; if the cap is hit, the agent raises a severity alert and support contacts the client while backups fall back to the local disk.
VerificationThe cloud checks that every client's latest backup and WAL stream are fresh, runs automated test restores on a schedule (Section 12), and alerts when a site's last good backup is older than its target.
RestoreTo a replacement server at the site, to a temporary cloud server, or to a chosen point in time to recover from a mistake. Restores are runbooked and timed.

6.2 Level C: remote access (the most requested)

ItemDesign
IdeaA remote user reaches the site's own server through the cloud gateway. There is one database, so there is nothing to merge and no conflicts. The same desktop app, and a web dashboard, point at the client's remote address.
PathUser to clientname.yourdomain.in (gateway: TLS, WAF, rate limits) to an encrypted tunnel that the site server opened outward, to the site's API. Authentication is the product's own (passwords, two-step sign-in), enforced on the site's server.
Tunnel technologyAn encrypted outbound tunnel such as WireGuard or an HTTPS reverse tunnel, one per site, with keys issued and revoked from the control plane. Decision: choose after a proof of concept (Section 21).
When the site is offlineThe gateway shows a clear status page ("your office server is offline; last seen ..."), and, for Hybrid Plus, offers read-only dashboards from the standby.
Access control per clientA client may restrict remote use by user, role, time, or country, require two-step sign-in for remote sessions, and see an audit of remote sign-ins. Remote sessions can be forced to read-only for given roles.
What remote users runThe desktop app over the internet works from day one. Phones: a responsive web "owner dashboard" (sales today, cash, receivables, stock alerts, approvals) is a separate, smaller build and the best answer to "remote use" requests; it is in the roadmap before the pilot.
PerformanceMumbai gateway to Indian client sites typically adds a modest delay; the tunnel carries only the app's API traffic. Heavy reports and exports are limited remotely by default and can be scheduled.
Abuse protectionRate limits per client at the gateway, request size limits, and automatic blocking of repeated failed sign-ins; the gateway never stores business data.
Trade-off to be aware of. In the simplest design the gateway terminates TLS so it can apply the WAF and rate limits, so it sees traffic in transit. Treat the gateway as a data processor in the data-processing agreements and harden it accordingly. An alternative, end-to-end TLS through the gateway, removes that visibility but gives up inspection and some protections.

6.3 Level B: live standby (Hybrid Plus)

ItemDesign
What it isA cloud PostgreSQL server that continuously replays the site's changes and can answer read-only queries. It lets owners view dashboards even when the office server is down, and it can be promoted to accept writes if the site server is lost.
HowStreaming replication from the site, over the same tunnel or a dedicated secure channel, using the PostgreSQL built-in mechanism. Typical lag is seconds when the internet is up; an alert fires if it exceeds a few minutes.
Failover (deliberate, not automatic)Failover is a runbook action with two checks: confirm the site primary is really down or lost, then promote the standby, point the client's remote address to it, and tell users. Automatic failover is avoided because a brief internet cut at the site would otherwise cause a "two primaries" situation.
FailbackWhen the site server is back or replaced, it is rebuilt from the promoted copy (a base backup), then roles are switched back in an agreed window. Until the switch, the site server must not accept writes.
ResourcesA running database per client is heavy. Assumption: a Hostinger server with 8 vCPU and 32 GB RAM hosts roughly 10 to 15 small standbys; so B is a paid upgrade, and capacity is planned in standby hosts.
What it does not doIt is not a backup: if bad data is written at the site, it is replicated too. That is why level A (point-in-time recovery) is separate and mandatory.

6.4 How A, B and C combine

EventWhat happens
Internet down at the siteThe office keeps working on the LAN. WAL queues locally. Remote access and cloud copies pause. On reconnect, queued WAL ships and standby catches up.
Site server disk fails (data lost)Restore from the cloud (A) onto a replacement, or promote the standby (B) for Hybrid Plus while the replacement is prepared.
Staff deletes or damages dataPoint-in-time recovery from level A into a temporary server; compare and recover with the client's approval.
Ransomware on the client networkCloud copies are unreachable for deletion; rebuild the server image, restore from A to a time before the attack.
Owner away from the officeLevel C through the gateway to the site's server; or read-only from the standby if the site is offline (Plus).
Your cloud is downSites keep working. Backups and WAL queue locally and ship later; remote access is unavailable until the gateway returns.

6.5 Why not two-way sync now

Allowing the site and the cloud to both edit the same data creates conflicts over document numbers, stock balances and ledger postings, which in an accounting system means corrupted books. The design avoids it by keeping one writer per client. The product already has the building blocks for safe sync later (immutable ledgers, idempotent writes, versioned records, an outbox of change events, offline POS batches). Section 17 describes the later design and the few cheap preparations to do now.

7.2 The fleet agent

DutyHow
HeartbeatEvery minute reports: version, database health, replication lag, backup age and WAL queue, free disk, tunnel status, last user activity, disk and memory health. The control plane marks sites healthy, degraded, or silent, and alerts.

Support accessA support session needs the client's approval (a button in the app or a code given by phone), has a time limit, uses the tunnel, is recorded, and ends automatically. No permanent inbound access.
OS and security patchesDelivered by the agent inside the maintenance window, tested first on staging and on your own site.
Self-protectionCannot disable its own audit; reports tamper signs (modified images, unexpected users); keeps a local ring buffer of logs for when the internet is down.

7.3 Operating 30 sites

  • Fleet screen with filters: version, ring, last heartbeat, backup age, disk, tunnel, open alerts, licence expiry.
  • Maintenance windows per site, with a calendar; no update outside it unless the client agrees.
  • Rings for releases (Section 11): your own site first, then friendly sites, then the rest.
  • Spare strategy: a few pre-imaged spare machines you can ship, or a cloud standby, to shorten recovery when a server dies.
  • Lifecycle: hardware refresh cycle (about 4 to 5 years), database major-version upgrades planned and tested on a copy, operating-system end-of-life tracking.
  • On-site visits are expected for installation, hardware faults, and sometimes upgrades; plan travel, partner technicians, or remote hands.

8.2 How we make a VPS estate trustworthy

  • Configuration as code: servers are built and changed by scripts (for example Ansible) stored in version control; no hand-edited servers; a server can be rebuilt in hours.
  • Network: default-deny firewall, only the gateway's web ports and tunnel ports open, management only through a private staff VPN, key-based access with no passwords, MFA for staff.
  • PostgreSQL we run: replication, automatic restarts, backups of its own, version pinning, extension minimalism, and routine vacuum and index maintenance monitored.
  • Patching: OS and package updates on a schedule, staging first.
  • Capacity: alerts at 70% for CPU, memory, disk and bandwidth; a monthly capacity review.
  • Independence from a single provider: DNS and domain at a separate provider; password vault, runbooks and infrastructure code in places Hostinger cannot take down; the off-provider backup copy; a tested plan to rebuild the gateway and control plane at another provider.

9.3 How it is enforced

On a site server the licence is a signed file the agent refreshes from the control plane (and caches), so enforcement works with no internet. The rules are the same everywhere:

  1. Server is the authority. Each API route is tagged with its module. A request whose tenant lacks that module is refused with a clear module_not_licensed error. Entitlements narrow permissions: a user can do something only if their role allows it and the module is licensed.
  2. Limits are checked at the point of creation (add user, add company, open a counter), with a friendly message and a path to upgrade, and recorded in usage metering.
  3. The app adapts. The sign-in response lists the licensed modules; the menu, command palette and screens hide anything not bought, and show a short "not in your plan" message for deep links.
  4. One schema for all. Every client's database has every table; unused modules are simply empty. Enabling a module is instant and never needs a data migration. Schema migrations run for everyone, always.
  5. Graceful removal. If a module lapses, its screens become read-only for a grace period (so a client can still export and reconcile), never deleted.
  6. Background work respects it too. Scheduled jobs, imports, API keys and webhooks for an unlicensed module stop.

9.4 Related per-client configuration (not licensing)

Industry templates (category trees), tax setup, numbering series, print layouts, discount limits and loyalty rates are configuration inside the tenant, set during onboarding. They stay separate from entitlements so support can adjust them without touching licences.

9.5 Feature flags for rollout

A separate, lightweight flag system lets you ship a new feature "dark", turn it on for your own tenant, then pilot clients, then everyone. Flags are for rollout safety and are removed after rollout; entitlements are for commercial scope and are long-lived.

11.2 The release train

  1. Cadence: regular releases (for example every two weeks), hotfixes on demand, and a stability freeze before month-end and financial year-end so no risky change lands in a client's busiest days.
  2. Gates: typecheck, lint, unit, integration and end-to-end tests, API contract check, dependency and image scans, a migration dry run on a copy of realistic data, and an upgrade-and-rollback test on the staging site.
  3. Signed release manifest: list of images, the migration, the minimum compatible client, release notes; signed so agents verify it.
  4. Rollout: ring 0, hold 48 to 72 hours, ring 1, hold, then ring 2 in batches; automatic halt if upgrade failures or error rates exceed thresholds.
  5. Per-site procedure: the safe upgrade steps in Section 7.2, within the maintenance window.

11.3 Database change rules

  • Expand, then contract: a migration only adds things the previous version can ignore. Removal happens a release later. This makes automatic application rollback safe at every site.
  • Migrations are rehearsed on realistic data and timed; large changes run in batches with visibility.
  • Replication-friendly: because standbys replay changes, upgrades are applied to the primary and flow to the standby; major PostgreSQL version upgrades are separate, planned projects per site.

11.4 Client and server compatibility

  • API versioning (/v1) with additive-only changes within a version.
  • Version handshake: the server states the oldest supported client version; the app says "update required" cleanly.
  • At most two server versions in the field; sites are expected to update within an agreed period (for example 60 days), after which support is limited.
  • Desktop apps update automatically but may be held to match a site that has not yet updated (the minimum and maximum compatible versions are in the manifest).

11.5 Flags and emergency switches

Risky features ship behind flags that support can turn off per site from the console in minutes. A per-site read-only switch exists for emergencies.

17. Later: multi-site and two-way sync (design preview)

You will later have clients with several sites (branches, warehouses, factories) that must share data, and you may want both the site and the cloud to accept edits. That is a major capability and the main reason to be careful now. The approach below is a preview, not a commitment; it will be designed in detail before the work starts.

17.1 Principles for later

  • One writer per record type per site (site of origin). A document is created at one site and owned by it. Other sites receive it. This avoids most conflicts by construction.
  • Append-only data replicates as events. Ledger entries, stock movements, invoices, receipts and payments are immutable; they are shipped as ordered, idempotent events (the product already has idempotency keys and an outbox of change events).
  • Derived values are recomputed, not copied. Stock on hand and balances come from movements and postings, so they converge.
  • Masters need conflict rules. Items, customers and prices can be edited at several sites: use versions, a field-level merge for harmless fields, and a review queue for real conflicts. Money-affecting fields (tax, price lists) can have a single owning site.
  • Numbering per site. Each site gets its own document number series so two sites never issue the same number; GST registration and financial-year rules are kept.
  • Topologies: a hub (head office site) with branches syncing up and down is the common case; a mesh is avoided.

17.2 Cheap preparations to do now

PreparationWhy nowSize
Introduce a site identity in the data model (a site id on documents and numbering, defaulting to the single site)Adding it later means rewriting history; adding it now is cheapM
Keep identifiers globally unique (UUID version 7 is already used) and never reuse numbersRequired for any mergeDone
Publish change events consistently for every write (outbox exists)Foundation for event-based syncM

  • Release notes written; support briefed; risky features behind flags.
  • Ring 0 and ring 1 updated and watched for the agreed period; failures and latency within bounds.
  • Rings updated in order (own site, friendly sites, then batches) inside each site's window; automatic halt thresholds watched.
  • Rollback plan confirmed (previous images, flags, pre-upgrade backup); previous installer retained.

Incident checklist

  • Declare, name the incident lead, open the channel and timeline.
  • Assess blast radius (which cells, which tenants); post an initial status update.
  • Contain: flag off, site read-only, roll back, or fail over to the standby per the runbook (two checks first).
  • Restore service; verify with real sign-in and a sample transaction.
  • Communicate resolution; keep evidence; schedule the blameless review within a week.
  • If personal data may be involved, notify the security owner immediately to follow the breach plan.
