1. Executive summary

You will serve between 50 and 100 clients, from one-shop retailers to larger multi-branch businesses, some of whom may insist on keeping data on their own premises. Not every client needs every feature. Your own IT team will run the platform. This plan is built on four ideas.

1. One codebase, one build, several deployment shapes. We never fork the product per client. A client differs from another only by where it runs (a shared cell, a dedicated stack, or their own server) and what is switched on (their entitlements). This keeps releases, fixes and support affordable at 100 clients.
2. Cells. A cell is a complete, self-contained deployment (application servers + its own database + storage + monitoring) that hosts many tenants. Pooled clients live in shared cells; a dedicated client is simply a cell with one tenant; an on-premise client is a cell on their hardware. A failure or a heavy client in one cell cannot affect another.
3. A small control plane above the cells. One central service knows every tenant, which cell it lives in, which modules and limits it has paid for, its licence, its release channel and its status. Cells ask it; support staff use it. This is what makes 100 different clients manageable by a small team.
4. Entitlements, not editions. Features are grouped into modules; each client has a signed entitlement record (modules, limits, expiry). The server enforces it on every request and the app hides what is not bought. The database schema is identical for everyone, so upgrading a client is a switch, not a migration project.

4. Deployment architecture

4.1 The shape: control plane above independent cells

4.2 Why cells instead of one big shared system

  • Blast radius. A bad release, a runaway report or a failed database in one cell affects only the tenants in that cell, not all 100 clients.
  • Predictable cost and capacity. You size a cell once, fill it, then add another. No large re-architecture to grow.
  • Dedicated and on-premise come for free. They are the same thing with fewer tenants, so there is no second product to maintain.
  • Rolling releases. Roll a release to the canary cell first (your own and friendly tenants), then the others.

4.3 How a client finds its cell

The desktop app already asks for a server address and a business code. Two options, and the plan recommends the first:

OptionHowTrade-off
A. One public address, routed (recommended)app.yourdomain.in in front of all pooled cells; the edge asks the control plane (cached) which cell serves the business code and forwards the request. Dedicated clients get a vanity name such as acme.yourdomain.in.Simple for clients and support; moving a tenant between cells is invisible. Needs the routing layer to be small, cached and reliable.
B. A different address per cellThe app is told which cell address to use for each business.Easier to build, but moves between cells need client reconfiguration, and support has more to explain.

4.4 What the control plane is, and is not

  • It is a small, separate service with its own database and its own staff-only access. It stores no client business data (invoices, stock, ledgers), only tenant metadata, entitlements, usage counts and the audit of admin actions.
  • If it is briefly unavailable, cells keep working: they cache each tenant's signed entitlements and keep serving. Only provisioning, plan changes and the support console pause.
  • Entitlements are signed by the control plane. A cell, including an on-premise one, verifies the signature with a public key, so a licence cannot be edited by hand, and an offline on-premise cell can run on a signed licence file.

Decision (important). Sales and POS post to the ledger. A small client who buys Sales but not Accounting still needs correct books underneath. Recommendation: the ledger engine is part of Core and always active; "Accounting" licenses the screens and reports (journals, chart editing, statements, periods), while Sales and POS continue to post using the default chart. That keeps data correct and makes upgrading a client a pure switch, with no data conversion.

5.3 How it is enforced

  1. Server is the authority. Each API route is tagged with its module. A request whose tenant lacks that module is refused with a clear module_not_licensed error. Entitlements narrow permissions: a user can do something only if their role allows it and the module is licensed.
  2. Limits are checked at the point of creation (add user, add company, open a counter), with a friendly message and a path to upgrade, and recorded in usage metering.
  3. The app adapts. The sign-in response lists the licensed modules; the menu, command palette and screens hide anything not bought, and show a short "not in your plan" message for deep links.
  4. One schema for all. Every client's database has every table; unused modules are simply empty. Enabling a module is instant and never needs a data migration. Schema migrations run for everyone, always.
  5. Graceful removal. If a module lapses, its screens become read-only for a grace period (so a client can still export and reconcile), never deleted.
  6. Background work respects it too. Scheduled jobs, imports, API keys and webhooks for an unlicensed module stop.

5.4 Related per-client configuration (not licensing)

Industry templates (category trees), tax setup, numbering series, print layouts, discount limits and loyalty rates are configuration inside the tenant, set during onboarding. They stay separate from entitlements so support can adjust them without touching licences.

5.5 Feature flags for rollout

A separate, lightweight flag system lets you ship a new feature "dark", turn it on for your own tenant, then pilot clients, then everyone. Flags are for rollout safety and are removed after rollout; entitlements are for commercial scope and are long-lived.

6. Hosting and infrastructure

6.1 Principles

  • India region and residency. Choose a cloud region in India for all client data by default. Offer on-premise for clients who need physical control.
  • Everything as code. Networks, databases, instances, DNS, alerts and access policies are written in infrastructure-as-code and reviewed like software. A cell can be rebuilt from code; no hand-made servers.
  • Managed services where possible. A small IT team should not run its own database cluster if a managed, multi-zone PostgreSQL service meets your needs. Spend effort on the application and operations, not on plumbing.
  • Separate everything that can be separated: per-cell credentials, encryption keys and networks; staging fully apart from production.

6.3 Capacity and cell sizing

Assumption, to be validated. I have not load-tested production-like data. Use these as planning numbers only: a pooled cell with 2 to 3 API instances (2 vCPU, 4 GB each) and a database of 4 to 8 vCPU, 16 to 32 GB RAM should comfortably carry 25 to 40 Starter and Business tenants. Therefore 50 to 100 clients is roughly 2 to 3 pooled cells plus a handful of dedicated ones. The existing performance script is the starting point: before the pilot, run it with realistic data volumes (several years of invoices, many items, busy counters) and set the real per-cell tenant cap from the results.

6.4 Capacity controls in a shared cell

  • Per-tenant rate limits and a cap on concurrent heavy reports so one client cannot starve others.
  • Statement and query timeouts in the database, and a read replica for reports when needed.
  • Tenant placement rules: large or fast-growing tenants are placed with fewer neighbours, or promoted to dedicated. The control plane records size and growth so this is a decision, not a surprise.
  • A tenant move tool (planned in the backlog) that copies a tenant's data to another cell and flips routing in a short, scheduled window.

6.5 Dedicated stack

The same code deployed from the same infrastructure templates, with one tenant. Differences are only: its own database and keys, optional standby in a second region, the client's chosen upgrade window, and (if needed) a private network connection or IP allow-list. Because it is the same artefact, a dedicated client can be demoted into a pooled cell, or a pooled client promoted, with the tenant move tool.

8.2 The release train

  1. Cadence: a regular release (for example every two weeks) plus hotfixes on demand. Fixed cadence beats ad hoc: clients and support know when to expect change.
  2. Gates: typecheck, lint, unit, integration and end-to-end tests, API contract check, security scans of dependencies and images, and a migration dry run on a copy of staging data.
  3. Roll-out order: staging, then the canary cell for 24 to 72 hours, then pooled cells one at a time, then dedicated cells in their windows.
  4. In each cell: run the migration image (as the owner role), then roll the new API instances gradually (rolling or blue-green), watching error rate and latency; automatic halt and rollback of the application if they worsen.
  5. Release notes for clients in plain language, and an internal changelog for support.

8.3 Database change rules (what keeps releases safe)

  • Expand, then contract. A migration may only add things the previous version can ignore. Removing or renaming happens a release later, after no running version uses the old shape. This makes rolling releases and instant app rollback safe.
  • Forward-only data. Ledgers are append-only, and migrations are not reversed. If a release goes wrong, you roll the application back and fix forward with a new migration.
  • Large changes in batches with time limits and visibility, never a table-locking surprise during business hours.
  • Every migration is rehearsed on staging data of realistic size, and its duration is recorded.

8.4 Client and server compatibility

  • API versioning (/v1) and the rule that changes within a version only add.
  • Version handshake: the server publishes the oldest client version it supports, and the app shows "update required" instead of failing mysteriously. (Backlog item.)
  • Support window: the server supports the current and previous client versions. Auto-update keeps nearly everyone on the current one; Enterprise clients that control their own roll-out get a longer window by contract.
  • Dedicated and on-premise clients may run at most one release behind the pooled cells, and are upgraded within an agreed period to keep your support matrix small (at most two server versions in the field).

8.5 Feature flags and emergency switches

Risky features ship behind flags. Support can turn a flag off per tenant or per cell in minutes without a deployment. A global "read-only" switch per cell exists for emergencies such as a data fix or a failed disk.

9.3 The hard problem: restoring one client in a shared database

If one client deletes or corrupts their own data, you cannot roll the whole shared database back without harming 30 other clients. The standard answer, and the one to build before go-live:

  1. Restore the database to the wanted moment in a separate, temporary instance.
  2. A tenant extraction tool reads that one tenant's rows (every table is tenant-keyed, which makes this possible) and produces a verified bundle.
  3. Either import the bundle into a fresh tenant for the client to compare, or, with the client's written approval, replace the damaged data in a controlled window.
The same extraction tool also powers client data export, tenant moves between cells, promotion to dedicated, and offboarding, so it is a high-value build.

9.4 Proving it works

  • Monthly automated restore test of the latest backup into a scratch instance, with data checks (ledgers balance, row counts, a sample tenant opens).
  • Quarterly disaster drill: rebuild a cell from code and the latest backup in a clean account, timed against the RTO. Failover drill yearly for Enterprise standbys.
  • Alerts when a backup is late, when log archiving lags, or when a restore test fails.

10.2 Legal and compliance (needs counsel)

  • India's Digital Personal Data Protection Act, 2023. For each client, decide the roles: normally the client is the data fiduciary and you are a data processor. Sign a data processing agreement that covers purpose, sub-processors (your cloud and email providers), security measures, breach notification, deletion and return of data, and cross-border rules.
  • Breach response: a written plan with roles, triage, client notification timelines, and regulator notification where required.
  • Contracts: master service agreement, service levels, acceptable use, privacy notice, and a clear statement of what is and is not guaranteed (for example, tax computations are client responsibility and need their accountant's review).
  • Accounting and tax software expectations: audit trail and immutability are already designed in; confirm the current Companies Act and GST audit-trail requirements with a Chartered Accountant before claiming compliance.
  • Certification path (optional, later): a security framework such as ISO 27001 or SOC 2 is often requested by large clients; start by documenting policies, then decide.
This section is an engineering plan, not legal advice. Treat the compliance points as a checklist for your lawyer and accountant to confirm.

11.4 Incident response

  1. Detect and declare (alert or report); an incident lead is named; a channel and a timeline start.
  2. Contain and restore first, investigate second. Use the runbooks (cell read-only switch, app rollback, flag off, failover).
  3. Communicate on a fixed rhythm through the status page and direct messages to affected clients.
  4. Post-incident review within a week, blameless, with owners and dates for fixes; share a summary with affected clients.

11.5 Support console (control plane)

Tenant search; plan, entitlements and limits; usage; version and last backup; recent errors; sign-in and lock status; resend invitations; reset two-step sign-in with verification; toggle flags; suspend or reinstate; start an audited "view as" session; trigger export. Every action is recorded with who, what, why.

11.6 Operating rhythm

  • On-call rota with a primary and a secondary, handover notes, and paid on-call for after-hours cover.
  • Weekly operations review (incidents, capacity, upcoming releases), monthly cost and capacity review, quarterly restore drill and access review.
  • A public or client-only status page and a maintenance calendar.

12.2 Billing operations

  • Annual or monthly plans in advance, GST invoices issued from your own OneSyncERP (a useful dogfood), payment by UPI, bank transfer or a payment gateway, with automated reminders.
  • Dunning ladder: reminder, past-due warning in the app, grace period, then read-only suspension (Section 7.1), then reinstatement on payment. No surprise data loss.
  • Plan changes take effect immediately in entitlements; downgrades honour a notice period.
  • Metering records active users, companies, locations, counters and monthly documents per tenant, feeding both billing and capacity planning.

12.3 Licence keys for on-premise

A signed file naming the tenant, modules, limits and expiry, verified offline by the public key built into the product. On expiry the system warns for a grace period and then becomes read-only; export always works. Renewal is a new file (or an automatic refresh when the server can reach the control plane).

Master service agreement, service level agreement per tier, data processing agreement, privacy notice, acceptable use, on-premise managed-service addendum, support policy, and a one-page security overview for sales. Have counsel review all of them.

Appendix C: checklists

Release checklist

  • All gates green (types, lint, unit, integration, end-to-end, API contract, scans).
  • Migrations are expand-only; dry run done on staging data; duration noted.
  • Release notes written; support briefed; risky features behind flags.
  • Canary cell updated and watched for the agreed period; error and latency within bounds.
  • Pooled cells updated one at a time; dedicated and on-premise scheduled.
  • Rollback plan confirmed (application version, flags); previous installer retained.

Incident checklist

  • Declare, name the incident lead, open the channel and timeline.
  • Assess blast radius (which cells, which tenants); post an initial status update.
  • Contain: flag off, cell read-only, roll back, or fail over per the runbook.
  • Restore service; verify with real sign-in and a sample transaction.
  • Communicate resolution; keep evidence; schedule the blameless review within a week.
  • If personal data may be involved, notify the security owner immediately to follow the breach plan.
