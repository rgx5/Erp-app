1. What the platform is

OneSyncERP is one product for selling, buying, stock, accounts, GST, payroll, production and leads, for Indian businesses from a single shop counter to a multi-location manufacturer. The same code runs on a client's own server, in a dedicated cloud stack, or in a shared cloud cell that holds about ten clients.

One codebase, switched by licence
What differs between clients is where it runs and which modules their licence turns on, never the code. Four editions (Starter, Growth, Enterprise, Manufacturing) are starting points; any licence can be adjusted per client.
The books are always correct
Every sale, purchase, stock movement and payroll run posts through one door into an append-only ledger that the database itself checks (debits equal credits, no edits, no deletes). Corrections are reversing entries.
Isolation enforced by the database
Each client's rows carry their client id and PostgreSQL's row-level security (forced, on every table) refuses to show one client another's data, even if application code had a bug.
Offline-capable counter
The billing counter keeps selling without internet and sends everything to the server when it returns.

2. The pieces and how they fit

  • Backend (backend/): a NestJS modular monolith on PostgreSQL 16. Stateless, so any number of instances can run behind a load balancer.
  • Desktop client (desktop-client/): Electron + React. Talks only to the API; holds an offline queue for the counter.
  • Control plane (control-plane/): a small central service that holds no client business data: clients and sites, signed licences, signed releases opened ring by ring, fleet health from agent heartbeats, staff accounts (with two-step sign-in) and their audit trail.
  • Fleet agent (agent/): runs on every site server, makes outbound calls only. Heartbeats every minute; applies signed releases only inside the site's maintenance window (backup first, migrate, switch, health check, roll back on failure); syncs licences; opens support access only when the client reads out a one-time code.
  • Gateway (gateway/): carries remote users' requests through the site's outbound HTTPS tunnel. Allows only /v1/* and /health/live, never /v1/platform/*. Stores nothing.
  • Deployment files (deploy/dokploy/): the cell stack (API, database, migrate, edge proxy, dump, backup, drill, retention), the control-plane stack, and deploy/monitoring/alerts.yml.

4. One database, many clients: how data stays separate

A cell is one PostgreSQL database shared by about ten clients (a "tenant" is a client). The design rules are enforced by the database and by automated tests, not by convention:

  • Every business table carries tenant_id as the first column of its primary key, and every foreign key includes it, so a row can never reference another client's row.
  • Row-level security is enabled and forced on every table with one policy: tenant_id = erp.current_tenant_id(), for the application role only. The tenant is set per transaction (set_config(..., true)), so a pooled connection cannot leak a client into the next request. A test fails the build if any table lacks the policy (only outbox_dispatch, schema_migrations and tenant_directory are outside it, deliberately).
  • The runtime role is weak on purpose: not a superuser, no BYPASSRLS, owns nothing, cannot create objects, and has no DELETE on business tables. The API refuses to start if that role is unsafe.
  • Per-client variable data (for example each client's lead fields, settings) lives in jsonb columns, so different clients need no different tables or releases.
  • The audit log and the ledger are append-only: triggers reject UPDATE/DELETE/TRUNCATE for every role.
What this does not isolate: performance (one client's heavy report shares the cell's CPU and database with the others; see section 10) and the blast radius of a lost cell (all its clients are affected together; see section 9 and the runbook). Each client's data can be copied to another cell exactly, which is the lever for both.

5. How the application is built

Request path

  1. The edge proxy (Caddy) terminates TLS and passes /v1/* to the API.
  2. Rate limit (optional, per address) → authentication (JWT or API key; default deny: every route must declare itself public or require a permission) → entitlement check (is the module licensed, is the licence read-only) → permission check.
  3. Interceptors: the per-client concurrency guardrail (section 10) and the request interceptor (request id, security headers, one access-log line, metrics).
  4. The handler runs inside one database transaction with the client set (uow.inTenant). Posting to the ledger, stock and the audit/outbox all happen in that same transaction, so a document and its accounting either all exist or none do.
  5. Errors are RFC 9457 problem documents with stable codes.

Conventions that keep it correct

  • Money and quantities are decimal strings, summed as integers of 1/10,000. No floating point anywhere near an amount; GST and TDS are integer paise arithmetic.
  • Idempotency: writes accept an Idempotency-Key; a retry returns the first result instead of posting twice (this is what makes the offline counter safe).
  • Transactional outbox: events are written with the business change and delivered afterwards by a relay (any number of instances may run it; failures retry with back-off and end in dead letters that alert).
  • One posting door (PostingService) and one stock door (StockService.move): sales, purchases, payroll, manufacturing, POS and manual journals all go through them, so period locks, control accounts and costing rules cannot be bypassed.
  • Document numbering per registration and financial year, gap-free where the law needs it.
  • Statutory rules live in code and in the database (GSTIN checksum, HSN/SAC formats, CGST = SGST = IGST/2, place of supply, TDS sections and thresholds), tested separately from the screens.

Modules

Sales (invoices, notes, orders, quotes, proforma, challan, recurring invoices, reminders), purchasing (orders, receipts, bills, TDS), inventory (stock ledger, batches, serials, reservations, transfers, counts, costing), POS (terminals, shifts, returns, gift cards, loyalty, offline), accounting (chart, periods, Schedule III statements, group consolidation), GST (GSTR-1, GSTR-3B, GSTR-2B reconciliation, GSTR-9 working, ITC register, e-invoice and e-way bill files), banking (statements in OFX/QIF/MT940/Excel, matching, reconciliation), approvals, payroll (statutory rules), manufacturing (BOM, work orders, job work, costing), extras (expenses, attachments, notifications) and leads (website, Meta and Google connectors, pipeline, territories, custom fields, conversion to customer).

6. The desktop application

  • Electron + React with a typed API client generated from the OpenAPI document; screens call only the API.
  • Offline counter: items and prices are held locally; sales queue with idempotency keys and flush on reconnect.
  • Printing: professional minimal documents (dark, heavy type for paper), thermal receipts (58/80 mm), label preview and direct printing; PDFs save to Documents and open in the default viewer.
  • Import: CSV, JSON, XML, Excel, zip bundles and exports from other accounting software (including .vyb), with column mapping and a dry run, read entirely on the client.
  • Hardware: cash drawer, serial weighing scale, customer display.
  • Languages: English, Hindi, Marathi, Gujarati. Updates: signed installers published as releases.

8. Releases, migrations and upgrades

Releases

Releases are signed manifests opened ring by ring: ring 0 is our own site, ring 1 friendly sites, ring 2 everyone. A site's agent upgrades only inside its maintenance window; the desktop app reads a MIN_CLIENT_VERSION from the server and asks older apps to update.

The migration standard

Database changes are forward-only SQL files (backend/db/migrations/NNNN_*.sql, checksummed) run by a separate migrate service as the table-owner role before the new API starts. Because a cell holds years of data for several clients, every migration after 0049 must pass an automated check (src/db/migration-policy.ts, run by the unit tests in CI) that blocks the patterns that lock or rewrite a large table or break the previous release during a rolling deploy:

BlockedWhyDo this instead
Add a NOT NULL column with no default; a volatile default (now(), random)Fails on a table with rows / rewrites the whole tableAdd nullable, backfill in batches, then add the constraint
Change a column type; SET NOT NULLRewrites or scans the table under a lockNew column + migrate data; or CHECK ... NOT VALID, VALIDATE, then SET NOT NULL
Add a CHECK or FOREIGN KEY that validates nowValidated under a lockAdd NOT VALID, then VALIDATE CONSTRAINT
CREATE INDEX on an existing table without CONCURRENTLYBlocks writes while it buildsCONCURRENTLY (outside a transaction)
Drop column/table, rename, TRUNCATE, LOCK, bulk UPDATE/DELETEBreaks the previous release; cannot be undone; long locksStop using it for one release first; batch from a maintenance job

A statement can be waived for a stated reason with a comment on the line before it (-- allow: blocking-index the table has under 10,000 rows); the waiver applies to that one statement. Changes to new tables are not restricted. Roll-back of the code is always possible because database changes only add; roll-back of the data is by restore (section 9).

Before a risky migration

  1. Take a fresh backup and note its label (pgbackrest info).
  2. Rehearse on a restored copy of the cell (runbook: Restore the whole cell to a scratch copy) and time it.
  3. Run during the cell's quiet window; watch erp_http_request_seconds and the pool gauges.

Retention (housekeeping)

A daily job removes expired idempotency keys (grace 24 h), delivered outbox events (30 days) and old sessions (180 days) in batches of 5,000. It never touches the audit log, ledgers or documents. Backups: 4 full and 7 differential kept (configurable).

10. Protecting other clients: limits and capacity

Per-client guardrails

  • Each client may have at most TENANT_MAX_CONCURRENT (default 60) requests running at once on a cell instance, and at most TENANT_MAX_CONCURRENT_HEAVY (default 4) of the heavy kind (reports, GST and TDS returns, exports, imports, ledgers). Over the limit the API answers 429 too_many_concurrent with Retry-After: 2; other clients are unaffected. 0 turns a limit off.
  • Statement timeout 15 s by default so one runaway query cannot hold the database; an optional per-address rate limit.
  • Usage per client: GET /v1/platform/tenants/:id/usage (row counts of the tables that grow) and the fleet view's 30-day document and event counts.

No partitioning or archiving has been built because the run did not show a need at this size; revisit when a client passes roughly 5 million ledger lines or a cell passes about 50 GB.

Found by the run: the whole-business JSON export is refused for a very large client (HTTP 413 above 200 MB). Use the client move tool (section 13) for large clients, and do not offer the JSON export as their only exit path.

12. Security

  • Sign-in: tenant + email + password (argon2id), optional TOTP two-step with single-use recovery codes, lock-out after repeated failures with identical responses for unknown and wrong accounts. Access tokens are 15-minute Ed25519 JWTs; refresh tokens are opaque, rotating, single-use, with reuse detection.
  • Authorization: roles hold permissions from a code-defined catalog (Appendix D); default deny; the built-in Owner role has the wildcard. API keys are hashed, shown once, scoped, revocable.
  • Secrets: DATA_ENCRYPTION_KEY encrypts stored secrets (TOTP seeds, connector keys) with AES-256-GCM bound to tenant and user; production refuses to start without the signing and encryption keys.
  • Network: TLS at the edge; the API is not exposed except through the edge proxy; /metrics and /v1/platform/* need the platform token; the gateway blocks platform paths and path tricks.
  • Staff access: control plane staff need two-step sign-in in production; support sessions need a code read out by the client; everything is audited.
  • Backups are encrypted on the server with a per-client or per-cell key; repositories hold only ciphertext; sites cannot delete their own history; the key escrow is split between two custodians.
  • Public intake endpoints (lead forms and Meta/Google webhooks) are keyed per connector, signature-checked where the source signs, and size/rate limited.

13. Operations runbook

Each procedure says when to use it, what you need, the steps, and how to know it worked. Commands assume the cell's compose stack is running on the server (cd to the stack's folder first). Names in <angle brackets> are yours to fill in.

13.0 Daily and monthly routine

  • Daily (5 minutes): look at the alert channel; open the fleet screen (silent or degraded sites, late backups); glance at erp_backup_wal_age_seconds and erp_job_last_ok for each cell.
  • Monthly: confirm the restore drill passed on every cell (erp_job_last_ok{job="drill"}); do one manual restore of a random client to a scratch copy and open its reports; review disk growth and the pool/throttle graphs; rotate nothing unless a secret is suspected.
  • Quarterly: a full cell restore rehearsal from the continuous backups (13.4) with the time written down; update the RTO row in section 9.

13.1 Check that backups are healthy

  1. curl -s -H "Authorization: Bearer $PLATFORM_ADMIN_TOKEN" http://127.0.0.1:8081/metrics | grep -E "erp_job|erp_backup"
  2. Expect erp_job_last_ok{job="backup"} 1, erp_backup_wal_age_seconds under 300, erp_backup_base_age_seconds under 90,000 (25 h).
  3. Details: docker compose exec backup pgbackrest --config=/etc/pgbackrest/pgbackrest.conf --stanza=cell info; integrity: same with verify.
  4. If log shipping is late: docker compose logs postgres | grep archive (usually bucket credentials, bucket unreachable, or disk full). While archiving fails, write-ahead logs pile up on the database disk: fix quickly or the disk fills.

13.2 Restore one client to a moment in time (undo a client's mistake)

Use when: a client (or we) posted or deleted something wrongly and the answer is "go back to 14:20 yesterday" for that client only. Other clients on the cell must keep working and keep everything done since.

  1. Agree the exact time with the client (with time zone). Pick a moment just before the mistake.
  2. Restore the cell to a scratch copy at that time (13.4, steps 1–3 with the time argument). The live cell is not touched.
  3. Look at the scratch copy: psql -h /restore/sock -p 5499 -U postgres -d erp; confirm the client's data is as it was (for example SELECT count(*) FROM erp.sales_invoices WHERE tenant_id = '<id>').
  4. Choose: (a) Fix forward (usually best): use the scratch copy to read the lost records and re-enter or reverse them in the live system (the ledger is append-only anyway). (b) Replace the client: put the client in read-only (13.6), export the client from the scratch copy (SOURCE_ADMIN_DATABASE_URL="postgresql://postgres@/erp?host=/restore/sock&port=5499" npm run maintenance:tenant-move -- export --tenant <id> --dir move-<id>), import it as a new client slug on the live cell, point the client at it, and keep the old one read-only for the audit trail. The move tool refuses to overwrite an existing client by design.
  5. Tell the client what was restored and what they must re-do (everything entered after the chosen time).
  6. Stop the scratch copy (pg_ctl -D /restore/data stop) and remove its volume.

Success: the client's reports for the affected period match what they expect; the other clients' latest documents are unchanged.

13.3 Move a client to another cell

Use when: a cell is full or noisy, a client outgrows pooling, or a cell must be emptied for maintenance. You need: the administrator (superuser) database connection of both cells; both cells at the same release (the tool compares migration heads); the target cell running and licensed in the control plane; time with the client for the cut-over (minutes for a small client, longer for a large one: rehearse).

  1. Prepare the target: the client must not already exist there (same id or slug). Check disk space (the client's size plus 30%) and that the target is at the same migration: npm run db:status on both.
  2. Rehearse without disturbing the client: export (step 4) while they work (the export reads one consistent snapshot), import with --dry-run on the target, which runs the whole load and rolls it back. Note the time each step took.
  3. Freeze: agree a window; put the client's licence in read-only (read the current licence with GET /v1/platform/tenants/<id>/entitlements and PUT the same modules and limits back with readOnly: true), so people can read but nobody writes. Wait for the outbox to drain (erp_outbox_pending = 0).
  4. Export from the source: SOURCE_ADMIN_DATABASE_URL=postgresql://postgres:…@source/erp npm run maintenance:tenant-move -- export --tenant <id> --dir /moves/<slug>. Output: one file per table and a manifest.json with row counts and checksums.
  5. Verify and copy: npm run maintenance:tenant-move -- verify --dir /moves/<slug>; copy the folder to a machine that can reach the target (it contains the client's data: use an encrypted channel and delete it afterwards).
  6. Import on the target: TARGET_ADMIN_DATABASE_URL=… npm run maintenance:tenant-move -- import --dir /moves/<slug>. It runs in one transaction, checks per-table counts and that the ledger balances, and rolls everything back on any difference. Included: all rows, attachments, users and password hashes, licence. Not included: sign-in sessions (people sign in again) and the pending event queue.
  7. Validate: GET /v1/platform/tenants/<id>/validate on the target (ledger balances, entries match lines, owner exists); sign in as the owner and open the trial balance, receivables and a recent invoice; compare to the source.
  8. Switch: in the control plane move the client's site record/address to the target cell; point the DNS or the desktop apps' server address; if the cell is shared, remove the licence from the source. People sign in again with the same passwords.
  9. Keep the source (read-only) for the agreed period (suggest 30 days), then retire it. Retiring is currently a manual database operation (see section 15): do not improvise it on a live cell.

If anything fails before step 8: nothing changed for the client except being read-only: set readOnly: false and stop. The import never partly applies.

13.4 Restore the whole cell (server lost or corrupted)

  1. Declare an incident; tell affected clients; note the time. If the server is gone, create a new VPS with the same compose stack and the same variables, including BACKUP_S3_* and BACKUP_CIPHER_PASS (from the secret manager; without the pass phrase the backups cannot be opened).
  2. Restore to a scratch copy first, even in an emergency, to check it is the right moment: on a one-off container of the database image with an empty /restore volume, run pitr-restore.sh (no argument = the newest state; or a time such as "2026-03-14 11:29:00+05:30"). It restores, starts the copy on port 5499 without archiving, and prints how to connect.
  3. Check: psql -h /restore/sock -p 5499 -U postgres -d erp -c "select max(id) from erp.schema_migrations" and a few client row counts; run restore-drill.sh's checks by hand if in doubt.
  4. Go live: with the application stopped, restore into the real data directory (pgBackRest restore with --delta, same arguments as the scratch restore but pg1-path the real one), start PostgreSQL, wait for recovery to finish (select pg_is_in_recovery() = false), run migrate, start api, check /health/ready.
  5. Re-establish backups immediately: the new timeline needs a new base backup (backup service does it at its first loop; confirm erp_job_last_ok{job="backup"} 1).
  6. Tell clients the time they were restored to; they must re-enter anything after it. Write the incident up, and record the elapsed time in section 9.

Scratch-copy and PITR logic are tested; the first real run on production hardware is still to be done: do it before the first client goes live.

13.5 Roll back a release

  1. Application only (the usual case; database changes only add, so the previous version still runs): in Dokploy open the service's Deployments and redeploy the previous one. On a site, the agent rolls back automatically if the post-upgrade health check fails; to force it, withdraw the release in the control plane (POST /releases/:id/withdraw) so no further site receives it, and redeploy the previous images on the affected sites.
  2. Desktop app: withdraw the installer release; set MIN_CLIENT_VERSION to the last good version only if the bad one must be refused (it forces an update prompt).
  3. Data written by the bad release is wrong: stop. Do not roll the database back. Use 13.2 for the affected clients with a time before the release.
  4. A migration failed half way: the migrate service stops and the API does not start (readiness reports "migrations are behind"); migrations run in a transaction where PostgreSQL allows it. Read the migrate log; fix forward with a new migration. Never edit an applied migration file (its checksum is stored).

13.6 Suspend, make read-only, reactivate a client

  • Suspend (nobody can sign in): POST /v1/platform/tenants/<id>/status {"status":"suspended","reason":"..."}; reactivate with "active". Both are audited and also available from the control plane.
  • Read-only (people sign in and read, nothing writes): set the licence readOnly: true (as in 13.3 step 3); an expired licence behaves the same after its grace period (default 14 days).

13.7 Onboard a new client on a cell

  1. In the control plane create the client and site (edition pre-fills the licence). Choose the cell with the most headroom (erp_tenants, erp_database_size_bytes, pool and throttle graphs): about ten per cell.
  2. Provision on the cell: POST /v1/platform/tenants with name, slug and owner (the agent or an operator does this); import the signed licence.
  3. Create the company, GST registration, locations and number series; load opening data with the import wizard; run GET /v1/platform/tenants/<id>/validate.
  4. Give the owner the app, the server address and a first password to change; enable two-step sign-in for owners.
  5. Within the first week confirm the client's data appears in the monthly drill's client count and in the next backup.

13.8 Offboard a client

  1. Confirm in writing; put the client in read-only; give them their data (the app's export for small clients, otherwise the move tool's folder to a drive).
  2. Suspend after the agreed period; keep the data for the contract's retention period (backups age out on their own schedule: 4 full backups ≈ one month).
  3. Purge: manual and not yet scripted (the application role cannot delete). Until it is, schedule it, have a second person approve, take a fresh backup first, and delete the client's rows as the administrator with row counts recorded. Remember backups still contain the client until they expire.

13.9 Rotate secrets

  • Platform token: set a new PLATFORM_ADMIN_TOKEN on every cell and in the agents/control plane; redeploy; the old value stops working immediately.
  • Signing key: add the old public key to AUTH_JWT_PREVIOUS_PUBLIC_KEYS, set the new private key, redeploy; remove the old key after 30 days (refresh-token lifetime).
  • Data encryption key: re-encrypting stored secrets is not automated: do not rotate without a migration plan.
  • Backup pass phrase: changing it makes older backups unreadable by new settings: start a new stanza/repository, keep the old pass phrase with the old repository until it expires.
  • Bucket keys: create new keys, update the cell variables, redeploy postgres and backup, confirm erp_job_last_ok{job="backup"} 1, revoke the old keys.

14. Quality: how we know it works

  • Backend: about 640 automated tests (unit tests plus integration tests that run against a real PostgreSQL 16 as the real restricted role through the real HTTP stack), including: every table has RLS, the schema mirror matches the migrations, migration rules, per-client limits, metrics, the restore and client-move paths, and the statutory calculations.
  • Desktop client: about 140 unit tests and 53 end-to-end tests (Playwright driving the real app), plus a smoke test of the built Electron app.
  • Control plane (43 tests), agent (real control plane + real pgBackRest and PostgreSQL when available) and gateway (real tunnel) have their own suites.
  • Capacity (npm run capacity) and perf baselines are opt-in runs; results above.
  • Restore drill runs monthly in production by itself.
Not yet verified on real systems: installers on real Windows and Mac machines (direct print, default PDF viewer, window controls), live Meta and Google lead delivery, a real Vyapar export, the S3 variant of the cell stack in a Docker daemon, a first full restore on production hardware, native-language text review (Hindi, Marathi, Gujarati), and the Meta app's approval.
